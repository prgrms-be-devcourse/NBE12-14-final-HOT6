4명, 4주, AWS 제외. 작업량은 기능별 가중치로 추정한 값이며(합계 약 95점, 1인당 약 24점) 정확한 수치가 아니라 균형 확인용이다.

## 3. 담당별 구현 내용

### A. 결제 코어 — 결제 및 동시성 제어
- **멱등키 처리**: 요청별 멱등키 검증, 중복 요청 방지, 같은 요청 재전송 시 기존 결과 반환, 같은 키에 다른 내용이면 거절
- **결제**: QR과 가맹점 검증, 지갑 차감(`WalletService.debit`), 캐시백 예산 예약(`CashbackService.reserve`), QR 사용 처리(`QrService.markUsed`), 결제 내역 저장. 월 한도 차감과 예산 확보까지 한 트랜잭션
- **결제 결과 재조회**: **멱등키 기반**(`GET /api/payments/by-key/{idempotencyKey}`). 결과를 모르는 상황에서는 결제 ID를 받지 못하므로 멱등키로 조회
- **결제 취소**: 취소 가능 여부 확인, 지갑 환급(`WalletService.credit`), 캐시백 적립 취소 및 예산 복원, 중복 취소 방지
- **사장님 결제 내역**: 가맹점별, 기간별 결제와 취소 내역. 일 정산과 같은 집계 기준(취소는 취소한 날 반영)
- **테스트**: 같은 멱등키 중복 요청, 같은 지갑의 동시 결제, 같은 예산에 대한 동시 예약, 실패 시 롤백

### B. 캐시백·예산·정책
- **정책 관리**: 요율과 기간 등록, 기간 겹침 금지, 결제 시점 적용 정책 결정, 변경 이력
- **적립 계산과 적립**: 데브머니 사용분 × 접수 시각 요율, 소수점 유지, 월 한도 차감, 적립 건 저장, 결제 취소 시 적립 취소
- **적립 지급 배치**: 결제 다음날 00:00 + 3일, 매시간 실행, 건별 트랜잭션, 대기에서 지급 완료로 조건부 갱신, 음수 캐시백 상계
- **연/월 예산 관리**: 연 예산, 월 예산 배정, 집행액과 잔여, 예약·차감·복원, 소진 시 적립 중단(결제는 진행)
- **예산 이월**: 월말 잔여 계산, 다음 달 이월, 이월 이력(`cashback_budget_transfer`), 연 총예산 초과 방지
- **예산 공지 후 중단/긴급 중단**: 대비금 기준(최근 7일 일평균 × 5일), 소모 시작 시 3일 후 중단 공지, 대비금 10% 남으면 긴급 중단
- **운영자 조회**: 월 예산 현황(월별 배정, 이월 유입, 집행, 예정, 잔여), 적립 내역 전체 조회(상태, 기간, 이용자 필터)
- **주요 테이블**: `cashback_annual_budget`, `cashback_monthly_budget`, `cashback_budget_transfer`, `cashback_policy`, `cashback_earning`

### C. 회원·지갑
- **회원**: 가입(모의계좌 1개와 지갑 생성, 초기 잔액 200만원), 로그인, 내 정보, 탈퇴 정산
- **인증**: JWT, 권한(USER / OWNER / ADMIN), 간편 비밀번호 6자리 검증, 5회 실패 시 잠금, 잠금 해제
- **지갑**: 조회(데브머니, 캐시백, 적립 예정 분리 표시), 충전, 환불(데브머니만), 거래 내역
- **이용자 캐시백 조회**: 월 한도 조회, 적립 내역 조회(`CashbackQueryService` 사용)
- **탈퇴 정산**: 음수 캐시백을 데브머니로 정산, 부족하면 계좌에서 충전, 남은 데브머니 환불. B와 합동 구현

### D. 가맹점·QR·정산·배포
- **가맹점**: 등록(증빙 서류 첨부 시 적립 대상 자동 승인, 사장님 승격, 점주당 1개)과 수정, 증빙 서류 나중 제출, 내 가맹점 조회, 이름 검색과 주변 검색(가맹점 찾기), 가맹점 전용 지갑·계좌 자동 생성. 승인·정지 상태 관리와 고정 QR은 제외(해지 상태는 가맹점 해지에서 다룬다)
- **QR**: 동적 QR 생성(3분 만료), 스캔 조회, 상태 조회(폴링), 결제 연동(`getPaymentTarget`, `markUsed`), 같은 QR 중복 사용 방지(조건부 UPDATE). 고정 QR 결제는 제외
- **일·월 정산**: 일 정산은 매일 00:10, 순매출(결제 - 취소) + 전일 이월, 음수면 0원 정산 후 이월, 가맹점·날짜별 중복 생성 방지. 월 정산은 매일 00:30에 전월 확정액을 합산해 가맹점 전용 지갑에 입금하고 계좌로 출금하며, 가맹점·정산월별 중복을 막는다. 점주용 조회와 운영자 수동 실행 API 포함
- **원장 대사**: 매일 00:50, 10종 독립 실행, 읽기만 하고 고치지 않음, 결과는 `reconciliation_result`에 저장, 수동 실행 API
- **가맹점 해지(탈퇴)**: 가맹점 상태(`ACTIVE`, `CLOSING`, `CLOSED`), 해지 미리보기와 신청, 신청 즉시 QR 생성·스캔·결제 대상 조회·검색 노출 차단, 해지 정산(마이너스 이월 차감, 남은 정산금을 점주 계좌로 바로 지급), 해지 대사. 결제 취소 차단은 A, 점주 탈퇴 허용과 가맹점 회원가입은 C
- **배포**: AWS(EC2, RDS, Terraform, nginx, HTTPS) 구성과 운영. 중간평가 이후 서버 역할과 SSM 접속, 22번 포트 폐쇄, GitHub Actions 기반 배포 자동화(저장된 키 없이 역할 사용)로 전환

## 6. 담당 간 연동 (인터페이스를 가장 먼저 확정)

| 연동 | 내용 |
|---|---|
| A ← C | 지갑 차감, 환급 (`WalletService.debit / credit`) |
| A ← B | 캐시백 예산 예약, 취소 (`CashbackService.reserve / cancel`) |
| A ← D | QR 사용 처리(`QrService.markUsed(qrToken, requestedAt)`), 결제 대상 조회(`getPaymentTarget`) |
| B → C | 캐시백 지급 시 지갑 적립 |
| C ← B | 월 한도, 적립 내역 조회 (`CashbackQueryService`). 계산과 상태 판단은 B, C는 응답 조립만 |
| D ← B | QR 스캔 조회에 필요한 요율, 남은 한도. 구현은 프론트가 B의 `GET /api/cashback/preview`를 직접 호출하는 방식으로 정리했다 |
| D ← A | 정산이 `payment`의 완료·취소 시각과 금액을 직접 읽는다(결제에서 매출 기록을 호출하지 않음) |
| D ← C | 대사가 계좌·지갑 원장을 읽고, 사장님 권한(OWNER)과 로그인한 회원 ID는 C의 인증을 쓴다 |
| D ↔ C | 가맹점 해지 완료 뒤 점주 탈퇴: D가 가맹점 상태를 조회로 제공하고, C가 점주 탈퇴(가맹점 없음 또는 `CLOSED`만 허용, 회원 행 잠금으로 가맹점 등록과 동시에 와도 안전하게)를 맡는다. 가맹점 상태 조회는 `MerchantService.findStatusByOwner`로 제공했다(#302). 점주 가입 때 개인 모의계좌가 만들어지고 해지 정산금이 그 계좌로 바로 들어간다. 세부는 #305, #306 |
| D → A | 해지 예정·해지 완료 가맹점의 결제 취소를 A의 취소 서비스가 가맹점 상태(`MerchantService.assertActive`)로 거절한다. 권한 규칙으로는 막을 수 없다. 결제 대상 조회는 D가 막는다 |

A와 B, A와 C의 연동은 가장 먼저 확정한다. B가 끝나기 전에는 A가 적립 0원 스텁으로 결제를 먼저 완성한다.

## 7. 협업 규칙
- 스키마 변경은 PR로만 한다. 전체 DDL은 B가 1주차 첫날 확정한다.
- 2주 말에 진행률을 점검하고, 여유가 있는 담당이 다른 담당의 일부를 가져간다.
- P1/P2는 개발 순서이며 생략 가능이라는 뜻이 아니다. 예산 확보 로직과 원장 대사는 필수다.
