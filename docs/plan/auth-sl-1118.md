# auth·wallet 도메인 기획 (회원·인증·지갑)

| 항목 | 내용 |
|---|---|
| 도메인 | 회원·인증·지갑 (패키지 `auth`, `wallet`) |
| 작성 | 이슬(C) · 2026-11-18 |
| 기준 문서 | 커밋된 [기획서](../project-spec.md), [역할 분담](../team-roles.md), [cashback 기획](cashback-mh-1118.md) |
| 상태 | 회원가입은 구현을 마쳤고 나머지는 진행 예정 |

**운영 방식**: [cashback 기획](cashback-mh-1118.md)의 방식을 따른다. 이 문서는 회원·지갑 도메인의 첫 기획 문서이며, 이후 변경은 새 날짜의 파일(`docs/plan/auth-이니셜-MMDD.md`)로 추가한다.

**도메인 방향(초안, 팀 합의 전)**: 돈과 개인정보는 안전하게 다룬다. 비밀번호·PIN은 평문으로 저장하지 않고, 잔액과 원장은 한 트랜잭션으로 함께 바꾸며, 같은 요청이 다시 와도 한 번만 처리한다.

**원칙**: MVP 구현이 최우선이다. 돈·개인정보와 관련된 규칙(암호화 저장, 한 트랜잭션, 멱등)은 처음부터 지키고, 부가 기능은 뒤로 미룬다.

**최근 갱신일** : 2026-11-18

## 한눈에 보기

- 회원가입(`POST /api/users/signup`)은 구현을 마쳤다. 모의계좌·지갑 생성은 후속 PR에서 붙인다.
- ERD는 `users.phone`을 11자, `users.email`을 100자로 줄였다.
- 가입 규칙을 새로 정했다. 비밀번호 8~15자, 전화번호는 하이픈 없는 숫자, 이메일은 공백 제거·소문자 변환, 가입 역할은 `USER` 고정이다.
- `ADMIN`과 `OWNER`는 일반 가입 뒤 DB에서 부여한다. 가맹점주 전용 가입은 두지 않는다. `OWNER`는 시민 기능도 쓰고, `ADMIN`은 운영 전용이다.
- PIN 잠금 해제는 이메일 인증번호로 한다.
- 충전은 토스페이먼츠(테스트 키) 결제창을 거친다(팀 합의). 결제가 승인되면 모의계좌에서 충전액이 빠지고 지갑에 같은 금액이 들어온다. 모의계좌 초기 잔액, 월 충전 한도, 보유 한도는 모두 100만원으로 통일했고, 부분 환불은 허용한다.
- 음수 캐시백은 캐시백으로만 상계한다(이후 캐시백 입금이 더해지며 상계). 충전한 금액(데브머니)으로는 상계하지 않으며, 그래서 데브머니와 캐시백 잔액은 분리한다. 탈퇴할 때도 음수 캐시백을 감수한다(팀 합의). 남은 데브머니는 모의계좌로 환불한다.
- 이용자 월 한도·적립 내역 조회는 B가 API까지 제공한다(이슈 #27). C는 제공하지 않는다.
- 지갑 `debit / credit`은 A의 결제와 B의 캐시백 지급·회수가 함께 호출한다. 시그니처와 잔액 구조는 합의가 필요하다([8절](#8-개발하면서-판단할-것)).

## 1. 기획서 대비 변경 요약

### 1-1. ERD 변경 (`users`)

| 컬럼 | 기존 | 변경 |
|---|---|---|
| `phone` | `VARCHAR(30)` | `VARCHAR(11)` (하이픈 없는 숫자만 저장) |
| `email` | `VARCHAR(255)` | `VARCHAR(100)` |

지갑 원장(`wallet_transaction`)에 `ref_key` 컬럼과 유니크 제약이 필요하다. 근거는 [3-5](#3-5-walletservice-ab-연동)절, 반영은 [5절](#5-데이터-모델-변경)이다.

### 1-2. 가입 규칙 추가

기획서에는 BCrypt 저장과 이메일 중복 불가만 있고, 아래 규칙은 없다.

| 항목 | 규칙 |
|---|---|
| 비밀번호 | 8~15자, 영문·숫자·특수문자(`!@#%^&*`)를 각각 1자 이상 포함, 허용 문자는 이 셋뿐 |
| 전화번호 | 하이픈 없는 10~11자리(`^01[0-9]{8,9}$`) |
| 이름 | 최대 100자(외국인 이름 고려) |
| 이메일 | 앞뒤 공백(전각 포함) 제거 + 소문자 변환 후 저장·중복 확인 |
| 가입 역할 | 서버가 `USER`로 고정하고 요청에서 `role`을 받지 않음. `ADMIN`과 `OWNER`는 일반 가입 뒤 DB에서 `role`을 직접 변경. 가맹점주 페이지는 `OWNER`만 접근하고, 가맹점주 전용 가입은 두지 않음 |
| 에러 코드 | `AUTH-001` 이메일 중복, `AUTH-002` 전화번호 중복(둘 다 409). 이후 기능에서 추가 |

**영향**

- 프론트: 비밀번호 안내 문구, 전화번호 입력 형식
- 로그인: 이메일에 같은 정규화를 적용해야 하고, 이메일로 조회하는 기능도 같다
- D(가맹점): `OWNER` 권한 검사와 `ownerId` 처리(가맹점 등록·수정 API)

### 1-3. 범위·확정

| 구분 | 내용 |
|---|---|
| 변경 | 가입 시 모의계좌·지갑 생성은 회원 저장 뒤 후속 PR에서 같은 트랜잭션으로 합친다 |
| 변경 | 이용자 월 한도·적립 내역 조회는 **B가 API까지 제공**한다(이슈 #27). 역할 분담에서 C로 적었던 항목을 B로 옮긴다. 지갑 화면에서 캐시백 상세가 필요하면 `refKey`(적립 건 ID)로 B의 조회를 쓰고, 화면 합성은 프론트에서 한다 |
| 확정 | 잠금 해제는 **이메일 인증번호로 해제한 뒤 PIN 재설정**한다(`AUTH-04`의 첫 안, 확정 필요 #2). 대체안(30분 자동 해제 또는 관리자 해제)은 이메일 발송이 막힐 때만 쓴다 |
| 확정 | **충전은 토스페이먼츠(테스트 키) 결제창을 거친다**(팀 합의). 결제가 승인되면 모의계좌에서 충전액이 빠지고 지갑에 같은 금액이 들어온다. 세부 설계는 [3-6](#3-6-토스페이먼츠-충전)절과 [8절](#8-개발하면서-판단할-것) |
| 확정 | **모의계좌 초기 잔액, 월 충전 한도, 보유 한도는 모두 100만원**으로 통일한다(확정 필요 #3, C 판단). **부분 환불 허용**(확정 필요 #4, 기본값 채택) |
| 확정 | **음수 캐시백은 캐시백으로만 상계**한다. 이후 캐시백 입금이 음수 잔액에 더해지며 상계되고, 충전한 금액(데브머니)으로 메우지는 않는다. 탈퇴할 때도 음수 캐시백은 정산하지 않고 감수한다(팀 합의). 기획서(AUTH-05)의 "음수 캐시백을 데브머니로 정산", "부족하면 계좌에서 충전", "음수가 남아 있으면 탈퇴 불가"는 적용하지 않는다. 남은 데브머니는 모의계좌로 환불한다([3-7](#3-7-탈퇴-정산)절) |
| 확정 | **데브머니와 캐시백 잔액은 분리**한다(ERD의 `balance`, `cashback_balance`). 캐시백 음수는 `cashback_balance`에서만 상계한다. B의 이슈 #27의 "한 잔액으로 합산" 문구는 분리로 정정을 요청한다 |

## 2. 도메인 범위와 구현 순서

기획서 ID는 커밋본의 ID다(AUTH-01 ~ 06, WAL-01 ~ 04, COM-03). 단계는 제안이다. [역할 분담](../team-roles.md)의 주차별 일정(C)과 같은 순서에서 가입과 `debit / credit`을 앞당겨 A의 결제 연동을 먼저 열어 준다. 팀 일정이 정해지면 조정한다.

### 단계 1. 가입·로그인·지갑 기반

- **U1 회원가입** (AUTH-01) `POST /api/users/signup`: **구현 완료**. 회원 저장까지
- **U2 가입 시 모의계좌·지갑 생성** (AUTH-01): U1과 같은 트랜잭션. 초기 잔액 100만원, 초기 지급 원장 기록, 중간에 실패하면 모두 롤백
- **U3 로그인·JWT** (AUTH-02) `POST /api/auth/login`: 토큰 방식은 확정 필요([8절](#8-개발하면서-판단할-것))
- **U4 인증·권한** (COM-03): JWT 필터, `SecurityConfig` 교체, 역할 `USER` / `OWNER` / `ADMIN`(`OWNER`는 시민 기능 포함, `ADMIN`은 운영 전용)
- **U5 내 정보 조회** (AUTH-06) `GET /api/users/me`: 이름, 역할, PIN 잠금 여부. 작아서 JWT 확인용으로 일찍 둔다
- **W1 `WalletService.debit / credit`** (A·B 연동): A의 결제·취소와 B의 캐시백 지급·회수가 호출한다([3-5](#3-5-walletservice-ab-연동)절)
- **W2 지갑 조회** (WAL-01) `GET /api/wallet`: 데브머니, 캐시백, 적립 예정을 따로 표시

**완료 기준**: 가입하면 모의계좌와 지갑이 생기고, 로그인 후 내 정보와 지갑을 조회한다. A가 `debit / credit`을 쓸 수 있다.

### 단계 2. PIN·충전·환불

- **U6 간편 비밀번호 검증** (AUTH-03) `POST /api/users/pin/verify`: 5회 실패 시 잠금, 성공하면 횟수 초기화. A의 결제가 호출하므로 결제 연동 전에 필요
- **W3 충전** (WAL-02) `POST /api/wallet/charges`: 멱등키, 한 트랜잭션, 월 충전 한도 100만원. 먼저 결제창 없이 모의계좌에서 지갑으로 충전하는 흐름으로 구현([3-4](#3-4-충전과-환불)절)
- **W4 환불** (WAL-03) `POST /api/wallet/refunds`: 데브머니만 가능, 부분 환불 허용
- **W5 거래 내역** (WAL-04) `GET /api/wallet/transactions`: 원장은 INSERT only

**완료 기준**: PIN을 5회 틀리면 잠기고, 충전·환불이 한 트랜잭션으로 처리되며 같은 멱등키는 한 번만 반영된다.

### 단계 3. 잠금 해제·탈퇴·토스페이먼츠

- **U7 잠금 해제** (AUTH-04) `POST /api/users/pin/unlock`: 이메일 인증번호 후 PIN 재설정
- **U8 탈퇴 정산** (AUTH-05) `POST /api/users/withdraw`, `withdraw/settle`: 탈퇴할 때는 음수 캐시백을 정산하지 않고 감수한다(팀 합의). 남은 데브머니는 모의계좌로 환불한다([3-7](#3-7-탈퇴-정산)절)
- **W6 토스페이먼츠 결제창 연동** (팀 합의): W3의 충전 앞에 결제 승인 단계를 붙인다([3-6](#3-6-토스페이먼츠-충전)절). API 경로는 충전 설계 때 정한다

**완료 기준**: 이메일 인증으로 잠금이 풀리고, 탈퇴 정산이 동작하며, 토스페이먼츠 테스트 결제가 승인되면 모의계좌 차감과 지갑 충전이 함께 일어난다. 일정이 막히면 U7(이메일 잠금 해제)을 먼저 줄인다(스펙의 대체안 사용).

### 단계 4. 통합·장애 테스트

- 가입 → 충전 → 결제 → 취소 → 환불 → 탈퇴 흐름의 통합 테스트
- 지갑 DB에 지연을 넣어 결제 트랜잭션이 롤백되는지 확인

**완료 기준**: 전체 흐름이 동작하고, 지갑 잔액이 원장 합계와 같다.

## 3. 확정한 설계

### 3-1. 회원가입

```text
POST /api/users/signup
  @Valid SignupRequest        (이메일 정규화는 검증보다 먼저 적용)
  AuthService.signup
    이메일·전화번호 중복 확인 → BusinessException (AUTH-001 / AUTH-002, 409)
    비밀번호·PIN BCrypt 암호화
    User.create(..., USER) → 저장
  SignupResponse              (id, name, email, role. 해시는 응답에 없음)
```

- 입력 검증은 [1-2](#1-2-가입-규칙-추가)절의 규칙을 따른다. PIN은 6자리 숫자다.
- 가입 직후 상태는 `ACTIVE`, PIN 실패 횟수 0, 잠금 시각 없음이다.
- U2를 붙일 때는 회원·모의계좌·지갑을 한 트랜잭션으로 저장하고, 하나라도 실패하면 모두 롤백한다.

### 3-2. 간편 비밀번호(PIN)

- 6자리 숫자이며 BCrypt로 저장한다.
- 검증에 실패하면 `pin_fail_count`를 올리고, 5회째에 `pin_locked_at`을 기록해 잠근다. 잠긴 동안은 검증을 거절하고, 성공하면 횟수를 0으로 되돌린다.
- 해제는 가입한 이메일로 인증번호를 보내고, 인증 후 PIN을 재설정하면 잠금과 횟수를 초기화한다.
- 구현 방침(제안): 틀렸을 때 예외로 롤백되면 올린 횟수가 사라지므로, 실패 횟수 저장은 롤백되지 않게 처리한다. 동시에 잘못된 PIN이 들어와도 5회를 넘겨 시도할 수 없도록 DB 락 또는 UPDATE 쿼리로 올린다.

### 3-3. 인증·권한

- 현재 `common/config/SecurityConfig`는 임시 설정이다(가맹점·가입·캐시백 운영자 경로만 열어 둠). 로그인·JWT를 구현하면 이 파일을 JWT 필터 설정으로 교체한다(파일의 TODO, COM-03).
- 가입 경로만 열고 `/api/users/**` 전체는 열지 않는다. 내 정보·PIN·탈퇴는 로그인이 필요하다.
- 인증·권한 실패(`COM-005` ~ `COM-008`)는 공통 에러 코드를 쓴다.
- 역할은 `USER` / `OWNER` / `ADMIN`이다. 가입하면 `USER`로 시작하고, `OWNER`와 `ADMIN`은 DB에서 부여한다.
- `role`은 값이 하나뿐이라, `OWNER`가 지갑·충전·결제 같은 시민 기능을 쓰도록 `OWNER`를 `USER`보다 위에 두는 역할 계층을 쓴다. 시민 기능 경로는 `USER`와 `OWNER`에게만 연다(`ADMIN`은 제외).
- `ADMIN`은 운영 전용이다. 시민 기능과 점주 기능은 쓰지 않으며, 시민 기능이 필요하면 따로 일반 계정을 쓴다.
- 역할을 바꾼 뒤에는 다시 로그인해야 새 역할이 적용된다(JWT의 역할은 로그인 때 정해진다).
- 가맹점주 페이지 진입 여부는 프론트가 `GET /api/users/me`의 `role`로 판단하고, 서버는 점주용 API를 `OWNER`로 제한한다.

| 역할 | 시민 기능(지갑·충전·결제) | 점주 기능 | 운영자 기능 |
|---|---|---|---|
| `USER` | O | X | X |
| `OWNER` | O (`USER` 포함) | O | X |
| `ADMIN` | X | X | O |

### 3-4. 충전과 환불

기획서(WAL-02, WAL-03)를 따르되, 아래를 확정했다.

- 충전은 토스페이먼츠 결제창을 거친다([3-6](#3-6-토스페이먼츠-충전)절). 결제가 승인되면 모의계좌에서 충전액을 차감하고 지갑에 같은 금액을 넣는다.
- 충전: 계좌 잔액 ≥ 충전액이어야 한다. **월 충전 한도와 보유 한도는 모두 100만원**이다(모의계좌 초기 잔액도 100만원으로 통일, C 판단으로 확정). 멱등키를 쓰고, 계좌 잔액·원장과 지갑 잔액·원장을 한 트랜잭션으로 바꾼다.
- 환불: 데브머니에서 모의계좌로 돌려준다. **충전금 일부만 환불할 수 있다(부분 환불 허용)**. 데브머니만 가능하고 캐시백·적립 예정은 불가하며, 음수 캐시백 상태에서도 허용한다(자동 정산하지 않음). 부분 환불은 부분 결제 취소와 구분한다.
- 원장은 INSERT만 한다. 취소는 새 행으로 추가한다.

### 3-5. WalletService (A·B 연동)

B의 요청(이슈 #27)을 기준으로 맞추는 안이며, **A·B와 합의 전**이다.

- 도메인 중립 시그니처: `credit(walletId, amount, type, refKey)`, `debit(walletId, amount, type, refKey, allowNegative)`. 캐시백은 `type`으로만 구분한다(`CASHBACK_EARN`, `CASHBACK_CLAWBACK`). `refKey`는 적립 건 ID다.
- 원장에는 `type`, `refKey`, 금액, 거래 후 잔액을 기록한다. 같은 `(type, refKey)`가 다시 오면 중복 반영하지 않고 예외 없이 정상 반환한다. 코드 조회만으로는 동시 요청을 막을 수 없어서 원장에 `(type, refKey)` 유니크 제약을 건다.
- 자체 트랜잭션을 새로 열지 않고 호출한 쪽 트랜잭션에 참여한다(`REQUIRED`). C에서 예외가 나면 A의 결제나 B의 건별 지급도 함께 롤백된다.
- 실패를 두 가지로 나눈다. 잔액 부족은 비즈니스 예외로 구분하고, DB 지연·락 대기 같은 시스템 장애는 감싸지 않고 그대로 전파한다. 반영할 수 없으면 예외를 던진다.
- 캐시백 회수는 `allowNegative=true`로 캐시백 잔액이 음수가 되는 것을 허용한다. 음수는 이후 캐시백 입금(`CASHBACK_EARN`)이 더해지며 상계되고, 충전한 금액(데브머니)으로는 상계하지 않는다.
- 잔액은 데브머니(`balance`)와 캐시백(`cashback_balance`)으로 분리한다. 캐시백 입금·회수(`CASHBACK_*`)는 캐시백 잔액을 바꾼다. 결제·취소가 두 잔액을 나눠 쓰는 방식은 A·B와 협의한다([8절](#8-개발하면서-판단할-것)).
- 남은 결정은 메서드 이름·반환 타입과 거래 `type` 이름이다([8절](#8-개발하면서-판단할-것)).

### 3-6. 토스페이먼츠 충전

도입과 전체 흐름은 팀 합의다. 서버가 지킬 것은 **제안**이며, 토스 API의 엔드포인트와 필드는 구현 전에 공식 문서로 확인한다.

```text
지갑 [충전] → 금액 입력 → [충전]
  서버: 계좌 잔액·월 충전 한도·보유 한도 검사 → charge 저장 (PENDING, pg_order_id, 금액)
  → 토스 결제창 (테스트 키) → 결제 수단 선택 → 결제
  → 성공 시 paymentKey · orderId · amount 가 돌아옴
  서버: 저장한 금액과 비교 → 토스 결제 승인 API 호출
  → 승인되면 한 트랜잭션으로
      모의계좌 −충전액 (계좌 원장 기록)
      지갑 +충전액 (지갑 원장 기록)
      charge 완료 (method 에 선택한 결제 수단 기록)
```

- 결제창을 열기 전에 계좌 잔액과 한도를 검사하고, 승인 직전에 한 번 더 확인한다. 결제를 마친 뒤 한도 때문에 실패하는 일을 줄이기 위해서다.
- 계좌 차감과 지갑 증가는 승인된 뒤 한 트랜잭션으로 한다. 승인 전에는 잔액을 바꾸지 않는다.
- 돌아온 `amount`를 믿지 않고 먼저 저장한 금액과 비교한다.
- 같은 `orderId`로 승인 요청이 다시 와도 계좌와 지갑에는 한 번만 반영한다.
- 승인은 성공했는데 계좌 차감이나 지갑 반영이 실패하면 토스 취소로 되돌린다.
- PG 승인액, 계좌 차감액, 지갑 증가액은 모두 충전액으로 같다. 토스 테스트 결제는 실제 돈이 움직이지 않으므로 모의계좌가 돈의 출처 역할을 한다.
- `charge.method`에는 결제창에서 고른 결제 수단을 기록한다(ERD의 `method` 컬럼).
- 환불은 기획서대로 데브머니를 모의계좌로 돌려주며, 토스 취소는 쓰지 않는다.
- 시크릿 키는 환경변수로 받고 레포에 올리지 않는다. 클라이언트 키만 프론트에 둔다.

### 3-7. 탈퇴 정산

- 남은 데브머니를 모의계좌로 환불하고, 상태를 `WITHDRAWN`으로 바꾸며 `withdrawn_at`을 기록한다.
- 탈퇴할 때는 음수 캐시백을 정산하지 않고 감수한다(팀 합의). 데브머니로 상계하지 않고, 계좌에서 충전해 메우지도 않으며, 음수가 남아 있어도 탈퇴할 수 있다.
- 평소에도 음수 캐시백은 충전한 금액(데브머니)으로 상계하지 않고 캐시백으로만 상계한다([3-5](#3-5-walletservice-ab-연동)절).
- 실행 전에 환불 금액을 안내하고 확인받으며, 실행 시 금액이 달라졌으면 다시 확인한다(기획서 AUTH-05).
- 멱등키를 적용한다(COM-01).
- 남은 양수 캐시백과 적립 예정의 처리는 MVP 이후다(이슈 #27).

## 4. 다른 담당과의 연동

- **A (결제)**
    - `WalletService.debit / credit` 시그니처와 예외 규칙, 트랜잭션 참여 방식([3-5](#3-5-walletservice-ab-연동)절)
    - A의 결제 기획 초안은 `debit` 반환값으로 데브머니·캐시백 사용분을 받는 형태라서 B의 요청과 맞춰야 한다([8절](#8-개발하면서-판단할-것))
    - 결제 시 PIN 검증(U6)을 호출하는 방식
    - 인증·권한 교체(U4)가 A의 API 보호에 영향
- **B (캐시백)**
    - 캐시백 지급: B의 스케줄러가 건별 트랜잭션 안에서 `credit(walletId, amount, CASHBACK_EARN, 적립 건 ID)`를 호출한다([cashback 기획 3-3](cashback-mh-1118.md))
    - 캐시백 회수: 지급된 캐시백의 결제가 취소되면 `debit(walletId, amount, CASHBACK_CLAWBACK, 적립 건 ID, true)`를 호출한다
    - 이용자 월 한도·적립 내역 조회는 B가 API까지 제공한다. C가 B를 호출하지 않아서 의존이 한 방향으로 유지된다(이슈 #27)
    - 음수 캐시백은 B가 보내는 캐시백 입금으로만 상계되고, 충전한 금액으로는 상계하지 않는다. 탈퇴할 때도 음수를 감수하기로 팀에서 합의했다. 남은 캐시백·적립 예정 처리는 MVP 이후다(이슈 #27)
    - 이슈 #27의 "데브머니와 캐시백을 한 잔액으로 합산" 문구는 분리(`balance`, `cashback_balance`)로 정정을 요청한다
- **D (가맹점·QR·정산·대사)**
    - `OWNER`는 별도 가입 없이 일반 가입 뒤 DB에서 부여한다. 가맹점 등록의 `ownerId`는 로그인한 사용자로 바꾸고, 가맹점 수정은 본인 가맹점만 허용한다(COM-03)
    - 원장 대사에서 지갑·계좌 잔액과 원장을 비교
    - 토스페이먼츠 충전에서도 계좌 차감과 지갑 증가가 함께 일어나므로 대사 규칙(계좌 차감액 = 지갑 증가액)은 그대로 쓴다. 필요하면 충전의 PG 승인액까지 같이 비교

## 5. 데이터 모델 변경

DB는 PostgreSQL 기준이다. 아래 외 컬럼은 ERD 그대로다.

- **`users`**: `phone` `VARCHAR(11)`, `email` `VARCHAR(100)`(ERD 수정 반영). 엔티티는 ERD와 같다(`id` BIGINT, `password_hash`, `pin_hash`, `pin_fail_count`, `pin_locked_at`, `role`, `status`, `withdrawn_at`, `created_at`).
- **변경 필요(제안)**: `wallet_transaction`에 `ref_key` 컬럼을 추가하고 `(type, ref_key)` 유니크 제약을 건다. B의 요청(이슈 #27)이며, 현재 ERD에는 `charge_id`, `refund_id`, `settlement_id`, `payment_id`만 있고 `ref_key`가 없다.
- **변경 없음**: `mock_account`, `wallet`, `charge`, `refund`, `withdrawal_settlement`. `wallet`은 `balance`(데브머니)와 `cashback_balance`(캐시백)를 분리해서 쓴다. `charge`의 `method`(결제창에서 고른 결제 수단), `pg_order_id`, `pg_payment_key`는 토스페이먼츠 충전에 쓴다.
- **미정**: 인증번호 저장(테이블 추가 시 ERD 수정, Redis면 의존성 추가), 리프레시 토큰 저장소([8절](#8-개발하면서-판단할-것)).

## 6. 증명할 불변 조건 (테스트)

- 비밀번호·PIN은 평문으로 저장되지 않는다(서비스 테스트로 확인).
- 같은 이메일·전화번호로 동시에 가입해도 한 건만 저장되고 나머지는 409로 응답한다(후속 구현 후 통합 테스트).
- 가입 중 일부 저장이 실패하면 회원·모의계좌·지갑이 모두 롤백된다.
- PIN을 5회 틀리면 잠기고, 실패 횟수가 롤백으로 사라지지 않으며, 동시에 틀려도 5회를 넘겨 시도할 수 없다.
- 충전·환불은 계좌 잔액·지갑 잔액·원장이 한 트랜잭션으로 바뀌고, 같은 멱등키는 한 번만 반영된다. 부분 환불 뒤에도 잔액과 원장이 일치한다.
- 같은 `(type, refKey)`로 `credit / debit`을 다시 호출해도 한 번만 반영되고 예외가 없다. 동시에 호출해도 마찬가지다.
- 토스페이먼츠 충전은 돌아온 금액이 저장한 금액과 다르면 거절하고, 같은 `orderId`는 한 번만 반영한다. PG 승인액, 계좌 차감액, 지갑 증가액은 같다.
- 탈퇴할 때 음수 캐시백이 남아 있어도 탈퇴되고, 남은 데브머니는 모두 모의계좌로 환불된다.
- 지갑 잔액은 원장 합계와 같다(D의 대사).
- `debit`에 지연·예외를 넣으면 호출한 결제 트랜잭션이 전체 롤백된다.

## 7. 제외·후순위

- 이용자 월 한도·적립 내역 조회 API: B가 제공(이슈 #27)
- 사장님(`OWNER`) 가맹점 정보 입력: 가맹점 도메인에서 담당(가입과 별개)
- `ADMIN`·`OWNER` 전용 가입 화면: 제외. 일반 가입 뒤 DB에서 `role`을 직접 변경
- `OWNER` 권한 신청·승인 기능: 제외. 시연에 필요하면 후순위로 자동 승인 API를 추가
- `ADMIN`의 시민·점주 기능: 제외(운영 전용). 필요하면 일반 계정을 따로 사용
- 한 계정이 여러 역할을 동시에 갖는 구조(역할 테이블): 제외
- 비밀번호 변경·찾기, 프로필 수정: 범위 밖(기획서에 없음)
- 소셜 로그인: 제외(기획서에 없음)

## 8. 개발하면서 판단할 것

번호는 우선순위가 아니라 식별용이다. 방향은 제안이다.

### 1. 로그인 토큰 방식과 리프레시 토큰 저장소

- **고민**: 확정 필요 #1. ERD에 리프레시 토큰 테이블이 없다.
- **방향**: 기본값은 Access / Refresh. 리프레시를 쓰면 저장 테이블(ERD 수정) 또는 Redis. 팀 확인 후 결정

### 2. PIN 잠금 해제의 인증번호 저장소와 메일 발송 방식

- **고민**: 인증번호와 만료 시각을 어디에 저장할지, 메일을 어떻게 보낼지
- **방향**: 저장은 테이블 또는 Redis, 발송은 SMTP. 개발 환경은 로컬 가짜 메일 서버로 시연할 수 있다. 막히면 스펙의 대체안(30분 자동 해제 또는 관리자 해제)

### 3. 탈퇴한 회원의 재가입

- **고민**: 같은 이메일·전화번호로 다시 가입할 수 있는지(`users`의 `unique`)
- **방향**: 정해지기 전까지 `unique`를 유지한다(재가입 불가)

### 4. 토스페이먼츠 충전 세부 설계

도입과 전체 흐름은 팀 합의이고, 아래 세부는 정해야 한다.

- **고민**
    - 결제창을 띄울 프론트 화면의 담당
    - 승인은 됐는데 계좌 차감이나 지갑 반영이 실패했을 때 토스 취소로 되돌리는 방식
    - `charge.method`에 기록할 결제 수단 값(토스가 돌려주는 값을 그대로 쓸지)
- **방향**: 프론트 담당은 팀에서 확인한다. 승인 후 실패는 토스 취소로 되돌린다. 결제창 없이 모의계좌에서 지갑으로 충전하는 흐름을 먼저 구현하고, 그 앞에 결제창을 붙인다

### 5. WalletService 시그니처와 거래 type 이름

- **고민**: A의 결제 기획 초안은 `debit(walletId, amount)`로 호출하고 데브머니·캐시백 사용분을 반환값으로 받는다(금액 `long`). B의 요청(이슈 #27)은 `debit(walletId, amount, type, refKey, allowNegative)`다. 메서드 이름, 반환 타입, 거래 `type` 이름은 C가 정한다.
- **방향**: B 요청의 도메인 중립 시그니처를 기준으로 하고, A가 필요한 데브머니·캐시백 사용분은 반환값으로 돌려주는 안. A·B와 협의. 거래 `type`은 `CHARGE`, `REFUND`, `PAYMENT`, `PAYMENT_CANCEL`, `CASHBACK_EARN`, `CASHBACK_CLAWBACK` 같은 이름을 제안

### 6. 동시 가입 시 unique 위반 처리

- **고민**: DB `unique` 위반이 지금은 500으로 응답된다.
- **방향**: 저장 시 예외를 잡아 중복 코드(409)로 변환한다. 구현하면서 통합 테스트로 확인

### 7. OWNER 권한 부여 방식과 토큰

- **고민**: `OWNER`를 DB에서 부여하면 이미 발급된 JWT는 옛 역할을 그대로 가진다. 시연에서 시민이 점주가 되는 흐름이 필요한지도 정해지지 않았다.
- **방향**: 역할을 바꾼 뒤 다시 로그인하는 것으로 한다. 시연에 필요하면 로그인한 사용자의 `role`을 `OWNER`로 바꾸는 자동 승인 API를 후순위로 추가한다
