| 도메인 | 회원·인증·지갑 (패키지 `auth`, `wallet`) |

| 상태 | 가입, 로그인(JWT access), 인증·권한, 내 정보, 지갑 조회·충전·환불 API, PIN 검증(결제 시 필수), 탈퇴(미리보기·실행·즉시 차단)는 구현을 마쳤다. 점주 가입·로그인 분리와 탈퇴 후 재가입은 설계를 확정했고 구현 전이다(이슈 #260, [3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절). 리프레시 토큰, 이메일 PIN 잠금 해제, 토스페이먼츠 충전, 점주 탈퇴는 이후다 |

**운영 방식**: [cashback 기획](cashback-mh-1118.md)의 방식을 따른다. 이 문서는 회원·지갑 도메인의 개인 기획서이며, 11/26에 파일명을 `auth-sl-1118.md`에서 `auth-ls-1126.md`로 바꿨고, 수정일은 머리표의 "최종 수정"에 적는다. 구현과 합의로 바뀐 내용이 많아 11/22와 11/24에 이 문서를 직접 고쳤다.

**도메인 방향(초안, 팀 합의 전)**: 돈과 개인정보는 안전하게 다룬다. 비밀번호·PIN은 평문으로 저장하지 않고, 잔액과 원장은 한 트랜잭션으로 함께 바꾸며, 같은 요청이 다시 와도 한 번만 처리한다.

**원칙**: MVP 구현이 최우선이다. 돈·개인정보와 관련된 규칙(암호화 저장, 한 트랜잭션, 멱등)은 처음부터 지키고, 부가 기능은 뒤로 미룬다.

**최근 갱신일** : 2026-11-26 (설계 반영, 구현 전: 점주 가입·로그인 분리, PIN 잠금 10분과 잠금 중 전체 차단, 탈퇴 정보 암호화 분리 보관, 재가입과 모의계좌 연결. 이슈 #260). 2026-11-24 (구현 반영: 로그인·JWT·인증 필터, `/me`, 지갑 API, PIN 검증과 결제 PIN 필수, 탈퇴 미리보기·실행·즉시 차단. 합의 반영: PIN 잠금은 MVP에서 30분 자동 해제, 리프레시 토큰·점주 탈퇴·재가입은 이후). 2026-11-22 (구현 반영: 가입 시 계좌·지갑 생성, `WalletService` 확정과 `debitPayment`·`creditPaymentCancel`, 충전 한도 검사, 충전 서비스. 합의 반영: 모의계좌 초기 잔액·보유 한도 200만원, 월 충전 한도 100만원. 지갑·계좌를 잠근 뒤 최신 값으로 다시 읽는 대응)

## 한눈에 보기

- **다음 변경(구현 전, 이슈 #260)**: 이용자와 점주의 가입·로그인을 분리하고, PIN 잠금을 10분으로 줄이며, 탈퇴 후 재가입을 허용한다. 설계는 [3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절에 있다. 아래 항목과 본문은 **지금 구현된 동작**이고, 바뀌는 곳에는 3-8을 표시했다.
- 회원가입(`POST /api/users/signup`)은 구현을 마쳤고, 가입하면 모의계좌(200만원)·가입 보너스 원장·지갑이 같은 트랜잭션으로 함께 만들어진다.
- ERD는 `users.phone`을 11자, `users.email`을 100자로 줄였다.
- 가입 규칙을 새로 정했다. 비밀번호 8~15자, 전화번호는 하이픈 없는 숫자, 이메일은 공백 제거·소문자 변환, 가입 역할은 `USER` 고정이다.
- `ADMIN`은 일반 가입 뒤 DB에서 부여하고, `OWNER`는 가맹점을 등록하면 자동으로 승격된다. 가맹점주 전용 가입은 두지 않는다. `OWNER`는 시민 기능도 쓰고, `ADMIN`은 운영 전용이다. **점주 가입 분리로 바뀐다([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절).**
- PIN은 6자리이고 5번 틀리면 잠긴다. **MVP에서는 잠긴 지 30분이 지나면 자동으로 풀린다(임시 방식).** 이메일 인증번호로 푸는 방식(U7)은 MVP 이후다. 결제할 때는 요청에 `pin`을 넣어야 하고 서버가 검증한다. **잠금 시간과 범위가 바뀐다([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절).**
- 로그인은 JWT access 토큰(30분)만 발급한다. **리프레시 토큰과 로그아웃은 MVP 중간 결과물 이후**로 미뤘다(이슈 #190).
- 탈퇴는 미리보기 → 실행 2단계이고, 탈퇴하면 토큰이 유효해도 다음 요청부터 막힌다. **점주 탈퇴는 이후에 한다.** 탈퇴한 회원의 **재가입은 [3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절에서 확정했다(구현 전).**
- 충전은 토스페이먼츠(테스트 키) 결제창을 거친다(팀 합의). 결제가 승인되면 모의계좌에서 충전액이 빠지고 지갑에 같은 금액이 들어온다. 모의계좌 초기 잔액은 200만원, 보유 한도는 200만원, 월 충전 한도는 100만원이다(두 한도는 운영자 설정, 하드 상한 이하로만 낮출 수 있다. 이슈 #69). 부분 환불은 허용한다.
- 음수 캐시백은 캐시백으로만 상계한다(이후 캐시백 입금이 더해지며 상계). 충전한 금액(데브머니)으로는 상계하지 않으며, 그래서 데브머니와 캐시백 잔액은 분리한다. 탈퇴할 때도 음수 캐시백을 감수한다(팀 합의). 남은 데브머니는 모의계좌로 환불한다.
- 이용자 월 한도·적립 내역 조회는 B가 API까지 제공한다(이슈 #27). C는 제공하지 않는다.
- 지갑 입금·차감은 A의 결제·취소(`debitPayment`, `creditPaymentCancel`)와 B의 캐시백 지급·회수(`credit`, `debit`)가 호출한다. 시그니처와 잔액 구조는 A·B와 합의해 구현했다([3-5](#3-5-walletservice-ab-연동)절).

## 1. 기획서 대비 변경 요약

### 1-1. ERD 변경 (`users`)

| 컬럼 | 기존 | 변경 |
|---|---|---|
| `phone` | `VARCHAR(30)` | `VARCHAR(11)` (하이픈 없는 숫자만 저장) |
| `email` | `VARCHAR(255)` | `VARCHAR(100)` |

C 담당(회원·지갑)이 쓰는 현재 ERD 전체는 [5절](#5-데이터-모델-현재-erd)에 있다.

### 1-2. 가입 규칙 추가

기획서에는 BCrypt 저장과 이메일 중복 불가만 있고, 아래 규칙은 없다.

| 항목 | 규칙 |
|---|---|
| 비밀번호 | 8~15자, 영문·숫자·특수문자(`!@#%^&*`)를 각각 1자 이상 포함, 허용 문자는 이 셋뿐 |
| 전화번호 | 하이픈 없는 10~11자리(`^01[0-9]{8,9}$`) |
| 이름 | 최대 100자(외국인 이름 고려) |
| 이메일 | 앞뒤 공백(전각 포함) 제거 + 소문자 변환 후 저장·중복 확인 |
| 가입 역할 | 서버가 `USER`로 고정하고 요청에서 `role`을 받지 않음. `ADMIN`은 일반 가입 뒤 DB에서 `role`을 직접 변경하고, `OWNER`는 가맹점 등록 시 자동 승격(이슈 #150). 가맹점주 페이지는 `OWNER`만 접근하고, 가맹점주 전용 가입은 두지 않음. **점주 가입 분리로 바뀐다([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절)** |
| 에러 코드 | `AUTH-001` 이메일 중복, `AUTH-002` 전화번호 중복(둘 다 409). 이후 기능에서 추가 |

**영향**

- 프론트: 비밀번호 안내 문구, 전화번호 입력 형식
- 로그인: 이메일에 같은 정규화를 적용해야 하고, 이메일로 조회하는 기능도 같다
- D(가맹점): `OWNER` 권한 검사와 `ownerId` 처리(가맹점 등록·수정 API)

### 1-3. 범위·확정

| 구분 | 내용 |
|---|---|
| 변경 | 가입 시 모의계좌·지갑 생성을 회원 저장과 같은 트랜잭션으로 합쳤다(구현 완료). 계좌에 초기 잔액을 넣는 기록을 남기려고 계좌 원장(`account_transaction`)을 이때 함께 추가했다 |
| 변경 | 이용자 월 한도·적립 내역 조회는 **B가 API까지 제공**한다(이슈 #27). 역할 분담에서 C로 적었던 항목을 B로 옮긴다. 지갑 화면에서 캐시백 상세가 필요하면 `refKey`(적립 건 ID)로 B의 조회를 쓰고, 화면 합성은 프론트에서 한다 |
| 확정 | **MVP에서 PIN 잠금은 30분 뒤 자동으로 풀린다**(사용자 결정, 임시 방식. 스펙 `AUTH-04`의 대체안). 이메일 인증번호로 해제하고 PIN을 재설정하는 방식(U7)은 MVP 이후다(확정 필요 #2). **11/26에 10분으로 바꾸기로 했다([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절)** |
| 확정 | **결제할 때 PIN은 필수**이고 서버가 검증한다. 틀리면 결제를 시작하지 않는다. 재조회(by-key)·충전·환불·탈퇴는 PIN을 요구하지 않는다(이슈 #187) |
| 확정 | **탈퇴는 2단계**(미리보기 → 실행)이고 점주·운영자는 탈퇴할 수 없다. 탈퇴하면 토큰이 유효해도 즉시 막는다([3-7](#3-7-탈퇴-정산)절, 이슈 #191). **점주 탈퇴는 이후**, **재가입은 11/26에 확정**([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절) |
| 확정 | **충전은 토스페이먼츠(테스트 키) 결제창을 거친다**(팀 합의). 결제가 승인되면 모의계좌에서 충전액이 빠지고 지갑에 같은 금액이 들어온다. 세부 설계는 [3-6](#3-6-토스페이먼츠-충전)절과 [8절](#8-개발하면서-판단할-것) |
| 확정 | **모의계좌 초기 잔액 200만원, 보유 한도 200만원, 월 충전 한도 100만원**이다(확정 필요 #3). 두 한도는 운영자 설정이며 하드 상한(200만원, 100만원) 이하로만 낮출 수 있다(이슈 #69). **부분 환불 허용**(확정 필요 #4, 기본값 채택) |
| 확정 | **음수 캐시백은 캐시백으로만 상계**한다. 이후 캐시백 입금이 음수 잔액에 더해지며 상계되고, 충전한 금액(데브머니)으로 메우지는 않는다. 탈퇴할 때도 음수 캐시백은 정산하지 않고 감수한다(팀 합의). 기획서(AUTH-05)의 "음수 캐시백을 데브머니로 정산", "부족하면 계좌에서 충전", "음수가 남아 있으면 탈퇴 불가"는 적용하지 않는다. 남은 데브머니는 모의계좌로 환불한다([3-7](#3-7-탈퇴-정산)절) |
| 확정(구현 전) | **이용자·점주 가입과 로그인 분리, PIN 잠금 10분, 탈퇴 후 재가입**(11/26, 이슈 #260). 내용은 [3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절 |
| 확정 | **데브머니와 캐시백 잔액은 분리**한다(ERD의 `balance`, `cashback_balance`). 캐시백 음수는 `cashback_balance`에서만 상계한다. B의 이슈 #27의 "한 잔액으로 합산" 문구는 분리로 정정되었다 |

## 2. 도메인 범위와 구현 순서

기획서 ID는 커밋본의 ID다(AUTH-01 ~ 06, WAL-01 ~ 04, COM-03). 단계는 제안이다. [역할 분담](../team-roles.md)의 주차별 일정(C)과 같은 순서에서 가입과 `debit / credit`을 앞당겨 A의 결제 연동을 먼저 열어 준다. 팀 일정이 정해지면 조정한다.

### 단계 1. 가입·로그인·지갑 기반

- **U1 회원가입** (AUTH-01) `POST /api/users/signup`: **구현 완료**. 회원 저장까지
- **U2 가입 시 모의계좌·지갑 생성** (AUTH-01): **구현 완료**. U1과 같은 트랜잭션. 초기 잔액 200만원, 계좌 원장에 가입 보너스(`SIGNUP_BONUS`) 기록, 중간에 실패하면 모두 롤백
- **U3 로그인·JWT** (AUTH-02) `POST /api/auth/login`: **구현 완료**. JWT access 30분. 리프레시 토큰·로그아웃은 MVP 이후(이슈 #190, [8절](#8-개발하면서-판단할-것))
- **U4 인증·권한** (COM-03): **구현 완료**. JWT 필터, `SecurityConfig` 교체, 역할 `USER` / `OWNER` / `ADMIN`(`OWNER`는 시민 기능 포함, `ADMIN`은 운영 전용), 소유권 공용 도구(`OwnedResources`)
- **U5 내 정보 조회** (AUTH-06) `GET /api/users/me`: **구현 완료**. 이름, 이메일, 역할(DB 현재 값), PIN 잠금 여부, 토큰 역할이 현재 역할과 다른지(`needsRelogin`)
- **W1 `WalletService`** (A·B 연동): **구현 완료**. `credit / debit`(B), `debitPayment / creditPaymentCancel`(A)([3-5](#3-5-walletservice-ab-연동)절)
- **W2 지갑 조회** (WAL-01) `GET /api/wallet`: 데브머니, 캐시백, 사용 가능 캐시백(음수면 0), 충전 한도 현황(보유 한도, 월 충전 한도, 이번 달 충전액, 남은 충전 가능액)을 표시한다. 적립 예정은 B의 적립 내역 API와 프런트가 합친다. **구현 완료**(서비스와 컨트롤러)

**완료 기준**: 가입하면 모의계좌와 지갑이 생기고, 로그인 후 내 정보와 지갑을 조회한다. A가 `debit / credit`을 쓸 수 있다.

### 단계 2. PIN·충전·환불

- **U6 간편 비밀번호 검증** (AUTH-03) `POST /api/users/pin/verify`: **구현 완료**. 5회 실패 시 잠금(30분 뒤 자동 해제), 성공하면 횟수 초기화. 결제 요청도 `pin`을 받아 같은 검증을 한다
- **W3 충전** (WAL-02) `POST /api/wallet/charges`: 멱등키, 한 트랜잭션, 보유 한도·월 충전 한도 검사. 먼저 결제창 없이 모의계좌에서 지갑으로 충전하는 흐름으로 구현([3-4](#3-4-충전과-환불)절). **구현 완료**(서비스, 컨트롤러)
- **W4 환불** (WAL-03) `POST /api/wallet/refunds`: **구현 완료**. 데브머니만 가능, 부분 환불 허용
- **W5 거래 내역** (WAL-04) `GET /api/wallet/transactions`: A가 구현했다(이슈 #169). 원장은 INSERT only

**완료 기준**: PIN을 5회 틀리면 잠기고, 충전·환불이 한 트랜잭션으로 처리되며 같은 멱등키는 한 번만 반영된다.

### 단계 3. 잠금 해제·탈퇴·토스페이먼츠

- **U7 잠금 해제** (AUTH-04) `POST /api/users/pin/unlock`: 이메일 인증번호 후 PIN 재설정. **MVP 이후**(MVP는 30분 자동 해제). 도입 전까지 자동 해제 시간은 10분으로 바꾼다([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절)
- **U8 탈퇴 정산** (AUTH-05) `POST /api/users/withdraw`, `withdraw/settle`: **구현 완료**(미리보기·실행·즉시 차단). 탈퇴할 때는 음수 캐시백을 정산하지 않고 감수한다(팀 합의). 남은 데브머니는 모의계좌로 환불한다([3-7](#3-7-탈퇴-정산)절). 재가입은 [3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절에서 확정했고(구현 전), 점주 탈퇴는 이후다
- **W6 토스페이먼츠 결제창 연동** (팀 합의): W3의 충전 앞에 결제 승인 단계를 붙인다([3-6](#3-6-토스페이먼츠-충전)절). API 경로는 충전 설계 때 정한다

**완료 기준**: 이메일 인증으로 잠금이 풀리고, 탈퇴 정산이 동작하며, 토스페이먼츠 테스트 결제가 승인되면 모의계좌 차감과 지갑 충전이 함께 일어난다. 일정이 막히면 U7(이메일 잠금 해제)을 먼저 줄인다(스펙의 대체안 사용).

### 단계 4. 통합·장애 테스트

- 가입 → 충전 → 결제 → 취소 → 환불 → 탈퇴 흐름의 통합 테스트
- 지갑 DB에 지연을 넣어 결제 트랜잭션이 롤백되는지 확인

**완료 기준**: 전체 흐름이 동작하고, 지갑 잔액이 원장 합계와 같다.

## 3. 확정한 설계

### 3-1. 회원가입

```text
POST /api/users/signup
  @Valid SignupRequest        (이메일 정규화는 검증보다 먼저 적용)
  AuthService.signup
    이메일·전화번호 중복 확인 → BusinessException (AUTH-001 / AUTH-002, 409)
    비밀번호·PIN BCrypt 암호화
    User.create(..., USER) → 저장
    WalletOpeningService.open(userId)   같은 트랜잭션: 모의계좌(200만원) + 계좌 원장(SIGNUP_BONUS) + 지갑(0원, ACTIVE)
  SignupResponse              (id, name, email, role. 해시는 응답에 없음)
```

- 입력 검증은 [1-2](#1-2-가입-규칙-추가)절의 규칙을 따른다. PIN은 6자리 숫자다.
- 가입 직후 상태는 `ACTIVE`, PIN 실패 횟수 0, 잠금 시각 없음이다.
- 회원·모의계좌·계좌 원장·지갑을 한 트랜잭션으로 저장하고, 하나라도 실패하면 모두 롤백한다(구현·테스트 완료). 응답에는 `walletId`를 넣지 않는다. 클라이언트가 알 필요가 없고, 로그인 이후에는 서버가 토큰에서 지갑을 찾는다.
- 비밀번호·PIN 암호화(BCrypt)는 아직 트랜잭션 안에서 한다. 밖으로 옮기는 정리는 [8절 11번](#11-가입-시-bcrypt를-트랜잭션-밖으로)에 둔다.

### 3-2. 간편 비밀번호(PIN)

- 6자리 숫자이며 BCrypt로 저장한다.
- 검증에 실패하면 `pin_fail_count`를 올리고, 5회째에 `pin_locked_at`을 기록해 잠근다. 잠긴 동안은 검증을 거절하고, 성공하면 횟수를 0으로 되돌린다.
- **해제(MVP, 임시)**: 잠긴 지 30분이 지나면 다음 검증 때 잠금과 횟수를 초기화하고 다시 시작한다. 이메일 인증번호로 해제하고 PIN을 재설정하는 방식은 MVP 이후(U7)이며, 코드 주석에도 임시 방식이라고 적었다.
- **변경 예정([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절)**: 잠금 시간을 10분으로 줄이고, 잠금 중에는 결제뿐 아니라 모든 기능을 막는다.
- **에러**: 틀리면 400 `AUTH-005`(메시지에 남은 횟수), 잠기면 409 `AUTH-006`(5번째로 틀려 잠기는 요청도 이 코드). 프론트가 401을 "토큰 만료"로 처리하므로 PIN 오류에는 401을 쓰지 않는다.
- **결제 연동**: 결제 요청 본문에 6자리 `pin`이 필수이고, 컨트롤러가 멱등키 검사 뒤 결제 파사드를 부르기 전에 검증한다. 틀리면 결제도 QR 사용도 일어나지 않는다. 결제 재조회(by-key), 충전, 환불, 탈퇴는 PIN을 요구하지 않는다.
- **구현**: 실패 횟수는 별도 트랜잭션(`REQUIRES_NEW`)으로 저장해, 호출한 쪽이 롤백돼도 올린 횟수가 사라지지 않는다. 횟수 증가와 잠금은 DB 조건부 UPDATE 한 문장이라 동시에 틀려도 5회를 넘지 않는다.

### 3-3. 인증·권한

아래는 지금 구현된 동작이다. 점주 가입을 분리하면 점주 승격과 역할 계층이 없어지고 권한 규칙이 바뀐다([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절).

- `common/config/SecurityConfig`는 JWT 필터 설정이다. 경로별 역할은 `SecurityConfigTest`의 권한 표가 지키고, 규칙에 없는 경로는 로그인만 하면 되며(`SecurityRuleCoverageTest`가 빠진 경로를 잡는다), 새 경로를 만들거나 바꾸면 전체 테스트를 돌려야 한다.
- 로그인·가입만 열고 `/api/users/**` 전체는 열지 않는다. 내 정보·PIN·탈퇴는 로그인이 필요하다.
- **탈퇴한 회원은 즉시 막는다.** 토큰은 만료(30분)까지 유효하므로, 인증 필터가 토큰을 해석한 뒤 매 요청 DB에서 탈퇴 여부를 확인하고(존재 여부만 묻는 쿼리 1번) 탈퇴했으면 인증을 만들지 않고 401 `AUTH-004`를 남긴다. 로그인·가입 같은 열린 경로는 그대로 통과하고, DB에 없는 회원은 막지 않는다.
- 인증·권한 실패(`COM-005` ~ `COM-008`)는 공통 에러 코드를 쓴다.
- 역할은 `USER` / `OWNER` / `ADMIN`이다. 가입하면 `USER`로 시작하고, **`OWNER`는 가맹점을 등록하면 자동으로 승격**된다(승인 절차 없음, 가맹점 등록과 같은 트랜잭션, 이슈 #150). `ADMIN`은 DB에서 부여한다.
- `role`은 값이 하나뿐이라, `OWNER`가 지갑·충전·결제 같은 시민 기능을 쓰도록 `OWNER`를 `USER`보다 위에 두는 역할 계층을 쓴다. 시민 기능 경로는 `USER`와 `OWNER`에게만 연다(`ADMIN`은 제외).
- `ADMIN`은 운영 전용이다. 시민 기능과 점주 기능은 쓰지 않으며, 시민 기능이 필요하면 따로 일반 계정을 쓴다.
- 역할을 바꾼 뒤에는 다시 로그인해야 새 역할이 적용된다(JWT의 역할은 로그인 때 정해진다). `/api/users/me`의 `needsRelogin`이 `true`이면 토큰의 역할이 현재 역할과 다르니 프론트가 재로그인을 안내한다. 리프레시 토큰을 도입하면(MVP 이후) 재발급 때 DB의 현재 역할을 읽어 재로그인 없이 바꿀 수 있다.
- 가맹점주 페이지 진입 여부는 프론트가 `GET /api/users/me`의 `role`로 판단하고, 서버는 점주용 API를 `OWNER`로 제한한다.

| 역할 | 시민 기능(지갑·충전·결제) | 점주 기능 | 운영자 기능 |
|---|---|---|---|
| `USER` | O | X | X |
| `OWNER` | O (`USER` 포함) | O | X |
| `ADMIN` | X | X | O |

### 3-4. 충전과 환불

기획서(WAL-02, WAL-03)를 따르되, 아래를 확정했다.

- 충전은 토스페이먼츠 결제창을 거친다([3-6](#3-6-토스페이먼츠-충전)절). 결제가 승인되면 모의계좌에서 충전액을 차감하고 지갑에 같은 금액을 넣는다.
- 충전: 계좌 잔액 ≥ 충전액이어야 한다. **보유 한도는 200만원, 월 충전 한도는 100만원**이 기본값이다(운영자 설정. 하드 상한 이하로만 낮출 수 있고 이슈 #69). 멱등키를 쓰고, 계좌 잔액·원장과 지갑 잔액·원장을 한 트랜잭션으로 바꾼다.
- 한도 검사: 보유 한도는 `데브머니 잔액 + 충전액 ≤ 한도`(캐시백 잔액은 포함하지 않는다), 월 충전 한도는 `이번 달 충전 누적 + 충전액 ≤ 한도`(한국 시간 달력월, 지갑 원장의 이번 달 `CHARGE` 합계)이며 딱 한도와 같은 금액은 허용한다. **환불해도 월 충전 한도는 복원하지 않는다**(충전과 환불을 반복한 우회 방지). 한도를 낮춰도 기존 잔액·누적은 건드리지 않고 이후 충전만 거절한다. 검사는 `credit`이 아니라 충전 서비스에서 하므로 캐시백 지급(`CASHBACK_EARN`)은 한도 영향을 받지 않는다(구현 완료).
- 충전 서비스: `charge(walletId, amount, idempotencyKey)`가 지갑 → 계좌 순서로 잠그고, `charge` 기록을 저장한 뒤 계좌 원장(−)과 지갑 원장(+)을 남긴다. 두 원장의 `ref_key`는 충전 ID이고, 같은 지갑의 같은 멱등키는 `(wallet_id, idempotency_key)` 유니크와 지갑 잠금으로 한 번만 처리한다. 에러는 WAL-006 ~ 009다(구현 완료).
- 같은 멱등키로 금액이 다른 충전 요청은 거절한다. 같은 멱등키·같은 금액이면 기존 결과를 그대로 반환한다(COM-01, 기획서 케이스 1-2).
- 환불: 데브머니에서 모의계좌로 돌려준다. **충전금 일부만 환불할 수 있다(부분 환불 허용)**. 데브머니만 가능하고 캐시백·적립 예정은 불가하며, 음수 캐시백 상태에서도 허용한다(자동 정산하지 않음). 부분 환불은 부분 결제 취소와 구분한다.
- 원장은 INSERT만 한다. 취소는 새 행으로 추가한다.

### 3-5. WalletService (A·B 연동)

A·B와 합의했고 구현을 마쳤다(이슈 #27, 이슈 #68).

| 메서드 | 호출 | 하는 일 |
|---|---|---|
| `credit(walletId, amount, type, refKey)` | B 지급, 충전 | 입금 |
| `debit(walletId, amount, type, refKey, allowNegative)` | B 회수 | 차감. 캐시백 회수만 `allowNegative=true` |
| `debitPayment(walletId, 충전금, 캐시백, paymentId)` | A 결제 | 충전금·캐시백 사용분을 한 번에 차감 |
| `creditPaymentCancel(walletId, 충전금, 캐시백, paymentId)` | A 결제 취소 | 결제 때 낸 칸 그대로 환급 |

모두 반환값이 없고, 자체 트랜잭션을 새로 열지 않고 호출한 쪽 트랜잭션에 참여한다(`REQUIRED`). C에서 예외가 나면 A의 결제나 B의 건별 지급도 함께 롤백된다.

| type | 바꾸는 잔액 | 방향 | 호출 |
|---|---|---|---|
| `CHARGE` | 데브머니 | 입금 | 충전 |
| `REFUND` | 데브머니 | 차감 | 환불(W4) |
| `PAYMENT_DEVMONEY` | 데브머니 | 차감 | A 결제 |
| `PAYMENT_CASHBACK` | 캐시백 | 차감 | A 결제 |
| `PAYMENT_CANCEL_DEVMONEY` | 데브머니 | 입금 | A 취소 |
| `PAYMENT_CANCEL_CASHBACK` | 캐시백 | 입금 | A 취소 |
| `CASHBACK_EARN` | 캐시백 | 입금 | B 지급 |
| `CASHBACK_CLAWBACK` | 캐시백 | 차감 | B 회수 |

어느 잔액을 바꾸는지는 type 이름이 아니라 `affectsCashback()`로 판단한다(`PAYMENT_CASHBACK`도 캐시백 잔액을 바꾼다).

- **원장**: `type`, `refKey`, 부호 있는 금액(입금 +, 차감 −, 호출자는 항상 양수로 요청), 거래 후 잔액을 기록한다. 같은 `(type, refKey)`가 다시 오면 반영하지 않고 정상 반환한다. 지갑 행을 잠근 안에서 확인하고 원장 `(type, ref_key)` 유니크 제약도 건다.
- **결제**: `debitPayment`는 충전금·캐시백 사용분을 한 트랜잭션에서 함께 차감하고, 한쪽이 부족하면(충전금 WAL-004, 캐시백 WAL-005) 둘 다 롤백한다. 0원인 쪽은 원장을 만들지 않고, 음수이거나 둘 다 0원이면 WAL-003이다. 캐시백 잔액이 0 이하이면 캐시백 사용액을 WAL-005로 거절한다(기획서 시나리오 8번).
- **취소 환급**: 환급 전에 같은 지갑·같은 결제 ID의 차감 기록이 있는지, 환급액이 그때 낸 금액 이하인지 확인한다. 어긋나면 호출 버그로 보고 `IllegalStateException`을 던진다.
- **캐시백 회수**: `allowNegative=true`로 캐시백 잔액이 음수가 되는 것을 허용한다. 음수는 이후 캐시백 입금(`CASHBACK_EARN`)이 더해지며 상계되고, 데브머니로는 상계하지 않는다. 데브머니는 `allowNegative`와 관계없이 항상 음수 불가다.
- **실패 구분**: 잔액 부족 같은 사용자 입력 오류는 `BusinessException`(WAL-001 ~ 009)으로 구분하고, 호출 버그(방향이 다른 type, 환급 한도 초과, 0 이하 금액의 엔티티 방어)는 `IllegalArgumentException`·`IllegalStateException`이다. DB 지연·락 대기 같은 시스템 장애는 감싸지 않고 그대로 전파한다.
- **탈퇴(`WITHDRAWN`)한 지갑으로는 `credit / debit`을 거절한다**(WAL-002). 탈퇴 처리가 지갑 행에 락을 걸고 상태를 바꾸므로, 거의 동시에 들어온 `credit / debit`은 락이 풀린 뒤 바뀐 상태를 보고 거절된다([3-7](#3-7-탈퇴-정산)절, 기획서 케이스 6).
- **낡은 엔티티 대응**: 잠근 직후 최신 값으로 다시 읽어, 같은 트랜잭션에서 먼저 읽은 객체의 낡은 잔액으로 다른 요청의 변경을 덮어쓰지 않는다([8절 9번](#9-지갑-잔액을-바꾸는-방식-낡은-엔티티-문제)).
- **락 순서**: 결제는 결제 행 → QR → 지갑 → 예산이고, 결제 취소는 QR을 잡지 않아 결제 행 → 지갑 → 예산이다. 충전·환불·탈퇴 정산은 지갑 → 계좌다.
- **호출하는 쪽 주의**: 지갑에서 던진 예외를 호출한 트랜잭션 안에서 잡고 계속 진행하면 트랜잭션이 롤백 전용이 되어 커밋 때 `UnexpectedRollbackException`이 난다. A는 실패 기록을 별도 트랜잭션(T3)에서 남기고, B는 건별 처리 메서드 밖(스케줄러)에서 예외를 잡는다.

### 3-6. 토스페이먼츠 충전

도입과 전체 흐름은 팀 합의다. 서버가 지킬 것은 **제안**이며, 토스 API의 엔드포인트와 필드는 구현 전에 공식 문서로 확인한다.

```text
지갑 [충전] → 금액 입력 → [충전]
  서버: 계좌 잔액·월 충전 한도·보유 한도 검사 → charge 저장 (PENDING, pg_order_id, 금액)
  → 토스 결제창 (테스트 키) → 결제 수단 선택 → 결제
  → 성공 시 paymentKey · orderId · amount 가 돌아옴
  서버: 저장한 금액과 비교 → 토스 결제 승인 API 호출
  → 승인되면 한 트랜잭션으로
      모의계좌 −충전액 (계좌 원장 기록)
      지갑 +충전액 (지갑 원장 기록)
      charge 완료 (method 에 선택한 결제 수단 기록)
```

- 결제창을 열기 전에 계좌 잔액과 한도를 검사하고, 승인 직전에 한 번 더 확인한다. 결제를 마친 뒤 한도 때문에 실패하는 일을 줄이기 위해서다.
- 계좌 차감과 지갑 증가는 승인된 뒤 한 트랜잭션으로 한다. 승인 전에는 잔액을 바꾸지 않는다.
- 돌아온 `amount`를 믿지 않고 먼저 저장한 금액과 비교한다.
- 같은 `orderId`로 승인 요청이 다시 와도 계좌와 지갑에는 한 번만 반영한다.
- 승인은 성공했는데 계좌 차감이나 지갑 반영이 실패하면 토스 취소로 되돌린다.
- PG 승인액, 계좌 차감액, 지갑 증가액은 모두 충전액으로 같다. 토스 테스트 결제는 실제 돈이 움직이지 않으므로 모의계좌가 돈의 출처 역할을 한다.
- `charge.method`에는 결제창에서 고른 결제 수단을 기록한다(ERD의 `method` 컬럼).
- 환불은 기획서대로 데브머니를 모의계좌로 돌려주며, 토스 취소는 쓰지 않는다.
- 시크릿 키는 환경변수로 받고 레포에 올리지 않는다. 클라이언트 키만 프론트에 둔다.

### 3-7. 탈퇴 정산

탈퇴는 2단계다(이슈 #191, 구현 완료).

| 경로 | 하는 일 |
|---|---|
| `POST /api/users/withdraw` | **미리보기**. 환불 예정액(남은 데브머니), 소멸될 적립 예정 건수·금액, 캐시백 잔액을 돌려준다. 아무것도 바꾸지 않는다 |
| `POST /api/users/withdraw/settle` | **실행**. 헤더 `Idempotency-Key`와 본문 `{ "expectedRefundAmount": 50000 }`. 그 사이 금액이 달라졌으면 409 `AUTH-008`로 거절하고 다시 확인하게 한다 |

실행은 한 트랜잭션이고, 중간에 실패하면 모두 롤백한다.

1. **지갑 행 잠금**(`findByIdForUpdate`). 이 트랜잭션에서 지갑을 가장 먼저 읽는 곳이어야 최신 잔액을 본다. 탈퇴 중에 들어온 `debit / credit`은 락이 풀릴 때까지 기다렸다가, 탈퇴가 먼저 끝났으면 바뀐 상태(`WITHDRAWN`)를 보고 거절된다(WAL-002, 기획서 케이스 6)
2. **남은 데브머니를 모의계좌로 환불**한다. 기존 `RefundService.refund`를 쓰고(원장 기록), 멱등키는 사용자가 환불 API에 쓴 키와 겹치지 않게 탈퇴 전용 값으로 만든다
3. **PENDING 적립 예정 건을 건별로 소멸**시킨다. B의 `CashbackService.cancel(paymentId)`를 건마다 호출하고, 결제 때 확보한 예산은 '남음'으로 돌아온다. 이렇게 하지 않으면 예산이 계속 묶이고, 3일 뒤 지급 배치가 탈퇴한 지갑에 캐시백을 넣는다. **이미 지급된(PAID) 건은 건드리지 않는다**(`cancel`이 PAID 건에 호출되면 지급한 캐시백을 회수해 버린다)
4. **지갑과 회원을 `WITHDRAWN`으로**, `withdrawn_at`을 기록한다. 회원은 객체를 고쳐 저장하지 않고 상태만 조건부 UPDATE로 바꿔서(PIN 실패 횟수 같은 다른 변경을 덮어쓰지 않음), 반영된 행이 0이면 이미 탈퇴한 것이라 모두 롤백한다

**정해진 것**

| 항목 | 값 |
|---|---|
| 음수 캐시백 | **정산하지 않고 감수**한다(팀 합의). 데브머니로 상계하지 않고 계좌에서 충전하지도 않으며, 음수가 남아 있어도 탈퇴할 수 있다 |
| 양수 캐시백 | 소멸 여부는 MVP 이후(이슈 #27). 이번에는 건드리지 않는다 |
| 점주(`OWNER`)·운영자(`ADMIN`) | **탈퇴 불가**(409 `AUTH-007`). 점주는 가맹점·정산 잔액이 있어 MVP에서는 막는다 |
| PIN | 요구하지 않는다(충전·환불과 같게, 이슈 #187) |
| 재가입 | MVP에서는 **불가**. 이메일·전화번호 `unique`를 유지하므로 가입은 `AUTH-001`/`AUTH-002`, 로그인은 `AUTH-004`다. **11/26에 허용으로 확정했다([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절, 구현 전)** |
| 이미 탈퇴한 회원의 재요청 | 401 `AUTH-004`. 두 요청이 동시에 들어와 둘 다 회원 확인을 통과한 경우에는 늦은 쪽이 지갑 잠금을 기다렸다가 409 `WAL-002`(또는 `AUTH-004`)로 거절된다. 어느 쪽이든 환불은 한 번만 일어난다 |
| 탈퇴 직후 | 토큰이 유효해도 인증 필터가 막는다(401 `AUTH-004`, [3-3](#3-3-인증권한)절) |

**알려진 한계 (MVP)**

탈퇴 PR 리뷰(A)에서 나온 내용이다. 발표 때 "알려진 한계"로 말한다.

| 한계 | 내용 | 대응 |
|---|---|---|
| **탈퇴한 회원의 결제를 점주가 취소할 수 없다** | 결제 취소는 이용자 지갑에 환급하는데(`creditPaymentCancel`), 탈퇴한 지갑은 WAL-002로 거절되어 취소가 계속 실패한다. 데브머니는 이미 모의계좌로 환불돼 돌려줄 곳도 없다. 지급이 끝난 캐시백의 회수(clawback)가 탈퇴한 지갑에서 막히는 것(이슈 #137 항목 4)과 같은 뿌리다 | **정책 미정**. 후보: ① 탈퇴 전에 취소 가능한 결제가 있으면 막기(취소에 기간 제한이 없으면 대부분 회원이 탈퇴할 수 없어 현실적이지 않다), ② 탈퇴한 지갑의 취소 환급을 모의계좌로 보내기(정확하지만 계좌 원장 type·대사 규칙 점검 필요, 캐시백 사용분은 계좌로 못 보냄), ③ 점주 취소는 허용하고 환급만 건너뛰기(가장 간단, 이용자는 환급을 못 받음). 결제 취소는 A의 영역이라 팀에서 정한다 |
| **같은 멱등키로 다시 요청하면 저장된 결과가 아니라 401 `AUTH-004`가 나간다** | 응답을 못 받은 클라이언트가 같은 키로 다시 요청하면 "이미 탈퇴"로 보일 뿐 `refundedAmount`를 확인할 수 없다. COM-01의 "같은 키면 기존 결과 반환"과 다르다. 환불은 한 번만 일어나므로 데이터는 안전하고 응답만의 문제다 | 프론트가 `AUTH-004`를 "탈퇴 완료"로 처리한다 |
| **양수 캐시백은 지갑에 남아 묶인다** | 탈퇴한 지갑은 쓸 수 없고 소멸시키지도 않는다 | MVP 이후(이슈 #27) |
| **적립 예정 건 중 하나라도 `cancel`이 실패하면 탈퇴 전체가 롤백된다** | 의도된 원자성이다. 다만 같은 원인으로 반복해서 탈퇴에 실패할 수 있다 | 운영자가 실패한 적립 건의 원인을 확인한다 |

#### 권한

- 역할 계층 `OWNER > USER`를 없앤다.
- `POST /api/merchants`는 `USER`에서 `OWNER`로 바꾼다.
- `GET /api/qr/limit`, `GET /api/qr/{token}/status`, `POST /api/users/pin/verify`는 `OWNER`에게도 연다. 점주의 QR 화면이 앞의 두 API를 쓴다.
- 결제 취소와 `/api/merchants/me/**`는 지금처럼 `OWNER`다.

#### PIN

- 점주도 로그인 후 PIN을 확인해야 첫 화면(결제 QR 생성)으로 이동한다. 지금은 PIN 확인 없이 바로 이동한다.
- 잠금 시간은 30분에서 10분으로 바꾼다. 상수 `PIN_LOCK_DURATION`과 에러 코드 `AUTH-006`을 그대로 쓴다. 로그인 토큰의 30분은 바꾸지 않는다.
- 인증 필터가 잠긴 계정의 API 요청을 `AUTH-006`으로 거절한다. 잠긴 지 10분이 지나면 잠기지 않은 것으로 본다. 로그인·가입 API는 잠금과 상관없다.

```text
탈퇴 (3-7의 실행 트랜잭션에 더한다)
  이름·이메일·전화번호를 AES-256-GCM 으로 암호화해 별도 테이블에 보관
  이메일·전화번호의 식별값(HMAC-SHA256) 저장
  users 의 이름·이메일·전화번호·비밀번호·PIN 을 빈 값으로 변경 (비밀번호·PIN 은 보관하지 않음)
  계좌와 거래 기록은 회원 ID 로 유지

가입
  같은 역할의 탈퇴 계정 중 이메일이나 전화번호의 식별값이 같은 것이 있는가
    없음 → 계좌 생성 (이용자는 초기 잔액 지급, 점주는 0원)
    있음 → 초기 잔액 없이, 가장 최근에 탈퇴한 계정의 계좌를 새 회원에게 연결하고 이전 회원 ID 를 기록
  이용자의 지갑은 새로 생성
```

- 계좌 원장은 바꾸지 않아 "계좌 잔액 = 원장 합"이 유지된다. 이전 회원 ID를 남겨, 연결한 뒤에도 거래가 누구의 것인지 따라갈 수 있게 한다.
- 새 계좌를 0원으로 만들지 않고 이전 계좌를 연결하는 이유: 계좌에 돈이 들어오는 길은 가입 지급과 환불뿐이라, 0원 계좌로는 충전할 수 없다.
- 회원 ID로 이름·연락처를 확인할 때는 운영자 전용 `GET /api/admin/users/{userId}/archive`(안)를 쓰고, 조회한 운영자·대상·시각을 기록한다.
- 탈퇴 계정은 이메일이 지워지므로 로그인은 일반 로그인 실패로 응답한다. `AUTH-004` 문구에서 "관리자에게 문의"를 지운다.

#### 화면

- 점주 가입 화면과 PIN 설정 단계를 추가한다. 이름 규칙과 비밀번호 붙여넣기 차단은 이용자 가입과 같다.
- 점주 로그인은 새 API를 쓰고 "이용자 계정이에요" 안내를 없앤다.
- 점주 PIN 확인 화면을 추가하고, 확인을 통과해야 점주 화면에 들어간다.
- 잠금 화면은 이용자·점주가 같은 내용을 쓴다. "지갑과 내역은 볼 수 있어요" 안내와 "내 지갑으로 돌아가기"를 없앤다. `AUTH-006`을 받으면 로그아웃 후 잠금 화면으로 보내고 각자의 로그인 화면을 안내한다.
- 가맹점 등록은 점주 로그인 후 들어가고, 등록 후의 "다시 로그인" 안내를 없앤다.
- 가입 동의와 탈퇴 화면에 보관 내용을 안내한다. 점주 가입 동의에는 "가맹점 정보는 5년 보관"을 더한다.

#### 데이터 변경

- 기존 `email`, `phone` 유니크 제약을 지우고 부분 유니크 인덱스를 SQL로 만든다. 엔티티의 `unique = true`도 지우고, 테스트 DB에도 인덱스가 만들어지게 한다.
- `users`에 `email_hash`, `phone_hash`, `previous_user_id`를 추가하고, 탈퇴 정보 보관 테이블과 조회 기록 테이블을 만든다.
- 암호화 키와 식별값 키를 환경 변수로 추가한다(`JWT_SECRET`과 별도). 키를 잃거나 바꾸면 보관 정보를 읽거나 재가입을 구분할 수 없다.
- 이미 탈퇴한 계정은 기존 제약을 지운 뒤 암호화 보관·식별값 저장·개인정보 삭제를 한 번 실행한다. 백업한 뒤 실행한다.

#### 알려진 한계

| 한계 | 내용 |
|---|---|
| 재가입 구분 | 이메일과 전화번호를 둘 다 바꾸면 처음 가입으로 본다 |
| 계좌 연결 | 본인인증이 없어, 전화번호를 물려받은 다른 사람이 이전 계좌의 잔액과 내역을 이어받을 수 있다 |
| PIN | 잠기기 전에는 서버가 PIN 확인 없이도 API를 허용한다(로그인 시점에 토큰 발급) |

| 기존 점주 | 지갑에 남은 데브머니·캐시백은 사용할 수 없다(시연 데이터 전제) |

## 4. 다른 담당과의 연동

- **A (결제)**
    - `debitPayment / creditPaymentCancel` 시그니처와 예외 규칙, 트랜잭션 참여 방식([3-5](#3-5-walletservice-ab-연동)절). A는 결제 요청에 `cashbackUsed`를 받고 T1에서 사용분을 저장한 뒤 T2에서 저장한 값을 한 번에 넘긴다(이슈 #55). 같은 결제 ID로 다시 호출하면 금액이 달라도 처음 값을 유지하므로 저장한 값 그대로 넘긴다
    - 락 순서는 결제 → QR → 지갑 → 예산이고, 결제 취소는 QR을 잡지 않아 결제 → 지갑 → 예산이다
    - 지갑 예외를 T2 안에서 잡고 계속하지 않는다(실패 기록은 T3)
    - 결제 시 PIN 검증(U6): 결제 요청(`PayRequest`)에 6자리 `pin`이 필수이고, `PaymentController`가 멱등키 검사 뒤 PIN을 검증한 다음 결제 파사드를 호출한다. 이 변경은 C가 직접 했다(A의 파일). 재조회(by-key)는 PIN을 요구하지 않는다(이슈 #187)
    - 인증·권한(U4)은 반영을 마쳤다. 결제 경로는 `walletId`를 요청이 아니라 토큰의 회원으로 찾고(`OwnedResources`), 임시 `permitAll`은 없다(A 기획서 합의 #7, #8, #15)
    - 점주 가입 분리 후에는 PIN이 잠긴 계정의 결제 요청도 인증 필터에서 `AUTH-006`으로 거절된다([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절, 구현 전)
- **B (캐시백)**
    - 캐시백 지급: B의 스케줄러가 건별 트랜잭션 안에서 `credit(walletId, amount, CASHBACK_EARN, 적립 건 ID)`를 호출한다([cashback 기획 4-3](cashback-mh-1118.md)). 구현을 마쳤고 B가 확인했다(이슈 #27, 닫음)
    - 캐시백 회수: 지급된 캐시백의 결제가 취소되면 `debit(walletId, amount, CASHBACK_CLAWBACK, 적립 건 ID, true)`를 호출한다. 회수 전에 같은 적립 건의 지급 기록을 지갑이 확인하지는 않는다(B가 `PAID`인 건만 회수)
    - 이용자 월 한도·적립 내역 조회는 B가 API까지 제공한다. C가 B를 호출하지 않아서 의존이 한 방향으로 유지된다(이슈 #27)
    - 음수 캐시백은 B가 보내는 캐시백 입금으로만 상계되고, 충전한 금액으로는 상계하지 않는다. 탈퇴할 때도 음수를 감수하기로 팀에서 합의했다. 남은 양수 캐시백 자체의 소멸 여부는 MVP 이후다(이슈 #27)
    - 충전 한도(이슈 #69): 한도 설정 저장소와 운영자 API는 B가 제공하고(`OperatorSettingService`), 충전에서 한도를 검사하는 부분은 C가 구현했다. `CASHBACK_EARN` 입금은 보유 한도 검사를 받지 않는다
    - **탈퇴한 지갑에는 입금이 WAL-002로 거절**된다. 그래서 탈퇴할 때 PENDING 적립 예정 건을 모두 소멸시켜, 지급 배치가 탈퇴한 지갑에 지급을 시도하지 않게 한다
    - **탈퇴 시 PENDING 적립 예정 건 소멸**: C가 탈퇴 트랜잭션 안에서 PENDING 건마다 `CashbackService.cancel(paymentId)`(PAY-03과 같은 메서드)를 호출해 확보 예산을 반환받는다(건별 호출로 확정, 구현 완료). 호출은 호출한 쪽 트랜잭션에 참여하고, 지급이 끝난(PAID) 건에는 부르지 않는다. 호출 규칙은 B가 확인해 주어야 한다([3-7](#3-7-탈퇴-정산)절)
    - 재가입하면 지갑이 새로 생겨 월 적립 한도가 처음부터 계산된다. 이어받을지는 B와 정한다([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절, 구현 전)
- **D (가맹점·QR·정산·대사)**
    - `OWNER`는 별도 가입 없이 가맹점을 등록하면 자동으로 승격된다. 가맹점 등록의 `ownerId`는 요청이 아니라 로그인한 사용자로 정하고(요청의 `ownerId`는 삭제), 가맹점 수정·QR·정산은 `/api/merchants/me/...`로 본인 가맹점만 다룬다. 점주당 가맹점은 1개다(COM-03, 이슈 #150)
    - 원장 대사에서 지갑·계좌 잔액과 원장을 비교한다. 지갑 원장과 계좌 원장의 `amount`는 둘 다 부호 있는 금액(입금 +, 차감 −)이라 같은 지갑·같은 잔액 종류의 `SUM(amount)`가 잔액과 같고, 계좌 원장에는 가입 보너스(`SIGNUP_BONUS`)가 포함된다
    - 충전은 계좌 원장(−)과 지갑 원장(+)이 같은 충전 ID를 `ref_key`로 가지므로 대사 규칙(계좌 차감액 = 지갑 증가액)을 충전 ID로 짝지어 비교할 수 있다. 토스페이먼츠 충전에서는 필요하면 충전의 PG 승인액까지 같이 비교

    - **점주 가입 분리([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절, 구현 전)**: 가맹점 등록은 점주 계정만 하고, `MerchantRegistrationFacade`의 점주 승격 호출을 없앤다. 점주 가입이 개인 모의계좌(0원)를 만든다

## 5. 데이터 모델 (현재 ERD)

C 담당이 쓰는 테이블 7개의 현재 구조다. 엔티티(코드)와 같고, DB는 PostgreSQL이다. 테이블 사이에는 **외래키 제약을 두지 않고** ID 값으로만 이어 둔다(JPA 연관관계 없음). 아래 "관계"는 논리적인 관계다. [3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절의 컬럼·테이블 추가와 제약 변경은 구현한 뒤 반영한다.

### 5-1. 테이블 관계

| 부모 | 자식 | 연결 컬럼 | 관계 |
|---|---|---|---|
| `users` | `account` | `account.user_id` | 1 : 1 (회원당 모의계좌 1개) |
| `users` | `wallet` | `wallet.user_id` | 1 : 1 (회원당 지갑 1개) |
| `account` | `account_transaction` | `account_transaction.account_id` | 1 : N (계좌 원장) |
| `wallet` | `wallet_transaction` | `wallet_transaction.wallet_id` | 1 : N (지갑 원장) |
| `wallet` | `charge` | `charge.wallet_id` | 1 : N |
| `wallet` | `refund` | `refund.wallet_id` | 1 : N |
| `charge` | 두 원장 | `ref_key` = `charge.id` | 충전 1건 = 계좌 원장 1행 + 지갑 원장 1행 |
| `refund` | 두 원장 | `ref_key` = `refund.id` | 환불 1건 = 계좌 원장 1행 + 지갑 원장 1행 |

다른 도메인이 지갑을 값으로만 참조한다: 결제(A)의 `payment.wallet_id`, 적립 건(B)의 `cashback_earning.wallet_id`, 월 한도(B)의 `cashback_monthly_limit`(지갑 ID로 이용자를 식별).

### 5-2. 테이블별 구조

**`users`** — 회원

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT PK | 자동 증가 |
| `name` | VARCHAR(100) NOT NULL | 이름 |
| `email` | VARCHAR(100) NOT NULL, UNIQUE | 앞뒤 공백 제거·소문자로 저장 |
| `password_hash` | VARCHAR(255) NOT NULL | 비밀번호 BCrypt |
| `phone` | VARCHAR(11) NOT NULL, UNIQUE | 하이픈 없는 숫자 |
| `pin_hash` | VARCHAR(255) NOT NULL | PIN(6자리) BCrypt |
| `pin_fail_count` | INT NOT NULL | PIN 연속 실패 횟수. 맞으면 0, 5가 되면 잠김 |
| `pin_locked_at` | TIMESTAMP, null | **잠긴 시각**. null이면 잠기지 않음. 잠긴 지 30분이 지나면 다음 검증 때 null로 되돌림(MVP, 임시) |
| `role` | VARCHAR(20) NOT NULL | `USER` / `OWNER` / `ADMIN`. 가입은 `USER`, 가맹점 등록 시 `OWNER`로 승격, `ADMIN`은 DB에서 부여 |
| `status` | VARCHAR(20) NOT NULL | `ACTIVE` / `WITHDRAWN` |
| `withdrawn_at` | TIMESTAMP, null | 탈퇴 시각 |
| `created_at` | TIMESTAMP NOT NULL | 수정 불가 |

**`account`** — 모의계좌(이용자당 1개)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT PK | |
| `user_id` | BIGINT NOT NULL, UNIQUE | 회원 |
| `balance` | BIGINT NOT NULL | 잔액. 가입하면 200만원, 보유 한도 200만원 |
| `created_at` | TIMESTAMP NOT NULL | |

**`account_transaction`** — 모의계좌 원장(INSERT only)

**`wallet`** — 지갑(이용자당 1개)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT PK | |

**`wallet_transaction`** — 지갑 원장(INSERT only)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT PK | |
| `wallet_id` | BIGINT NOT NULL | 지갑 |
| `type` | VARCHAR(30) NOT NULL | `CHARGE`, `REFUND`, `PAYMENT_DEVMONEY`, `PAYMENT_CASHBACK`, `PAYMENT_CANCEL_DEVMONEY`, `PAYMENT_CANCEL_CASHBACK`, `CASHBACK_EARN`, `CASHBACK_CLAWBACK`([3-5](#3-5-walletservice-ab-연동)절) |

| `charge_id`, `refund_id`, `settlement_id`, `payment_id` | BIGINT, null | 원인 행을 가리키려고 둔 컬럼이지만 **현재 채우지 않는다**(원인은 `ref_key`로 표시) |
| `created_at` | TIMESTAMP NOT NULL | |

`(type, ref_key)` 유니크(`uk_wallet_transaction_type_ref_key`)로 같은 원인이 두 번 반영되지 않게 한다. `ref_key`가 null이면 유니크에서 서로 중복으로 보지 않는다. `(wallet_id, created_at)` 인덱스. 같은 지갑·같은 잔액 종류의 `SUM(amount)`가 잔액과 같다(D의 대사).

**`charge`** — 충전

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT PK | |
| `wallet_id` | BIGINT NOT NULL | 지갑 |
| `amount` | BIGINT NOT NULL | 충전액 |
| `idempotency_key` | VARCHAR(64) NOT NULL | 멱등키 |
| `created_at` | TIMESTAMP NOT NULL | |

`(wallet_id, idempotency_key)` 유니크. 한 번 만든 충전은 바꾸지 않는다. 충전한 `charge.id`가 지갑 원장과 계좌 원장의 `ref_key`다.

**`refund`** — 환불(탈퇴 환불 포함)

| 컬럼 | 타입 | 설명 |
|---|---|---|
| `id` | BIGINT PK | |
| `wallet_id` | BIGINT NOT NULL | 지갑 |
| `amount` | BIGINT NOT NULL | 환불액(데브머니만) |
| `idempotency_key` | VARCHAR(64) NOT NULL | 멱등키. 탈퇴 환불은 탈퇴 전용으로 만든 값 |
| `created_at` | TIMESTAMP NOT NULL | |

`(wallet_id, idempotency_key)` 유니크. 환불한 `refund.id`가 지갑 원장과 계좌 원장의 `ref_key`다.

### 5-3. 규칙

- **원장은 INSERT만 한다.** 잔액은 원장 합계와 같고, 잘못된 기록은 고치지 않고 새 행으로 바로잡는다.
- **잠그는 순서**: 충전·환불·탈퇴는 지갑 → 계좌 순서로 행을 잠근다. 결제는 결제 행 → QR → 지갑 → 예산, 결제 취소는 결제 행 → 지갑 → 예산이다.
- **탈퇴**: 별도 정산 테이블 없이 `refund` 행, 두 원장, `users.status`·`users.withdrawn_at`, `wallet.status`로 남긴다([3-7](#3-7-탈퇴-정산)절).
- **회원 삭제는 하지 않는다.** 탈퇴해도 행은 남고 이메일·전화번호 `unique`가 유지되어 재가입은 불가하다. [3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절을 구현하면 행은 남기되 개인정보를 지우고 재가입을 허용한다.
- **이후 추가 예정**: `refresh_token`(이슈 #190), 이메일 인증번호 저장(U7), 토스페이먼츠용 `charge` 컬럼(`method`, `pg_order_id`, `pg_payment_key`, 상태).

## 6. 증명할 불변 조건 (테스트)

- 비밀번호·PIN은 평문으로 저장되지 않는다(서비스 테스트로 확인).
- 같은 이메일·전화번호로 동시에 가입해도 한 건만 저장되고 나머지는 409로 응답한다(후속 구현 후 통합 테스트).
- 가입 중 일부 저장이 실패하면 회원·모의계좌·계좌 원장·지갑이 모두 롤백된다(구현·테스트 완료).
- PIN을 5회 틀리면 잠기고, 실패 횟수가 롤백으로 사라지지 않으며, 동시에 틀려도 5회를 넘겨 시도할 수 없다.
- 충전·환불은 계좌 잔액·지갑 잔액·원장이 한 트랜잭션으로 바뀌고, 같은 멱등키는 한 번만 반영된다. 같은 멱등키로 금액이 다른 충전 요청은 거절된다. 부분 환불 뒤에도 잔액과 원장이 일치한다.
- 같은 `(type, refKey)`로 `credit / debit`을 다시 호출해도 한 번만 반영되고 예외가 없다. 동시에 호출해도 마찬가지다.
- 충전은 같은 지갑의 동시 요청에서도 보유 한도·월 충전 한도·계좌 잔액을 넘지 않고, 월 한도는 달이 바뀌면(KST) 0부터 다시 시작하며 환불해도 복원되지 않는다.
- 지갑·계좌를 잠그기 전에 먼저 읽었어도 잠근 뒤에는 최신 잔액으로 처리해, 다른 요청의 입금·차감이 사라지지 않는다.
- 토스페이먼츠 충전은 돌아온 금액이 저장한 금액과 다르면 거절하고, 같은 `orderId`는 한 번만 반영한다. PG 승인액, 계좌 차감액, 지갑 증가액은 같다.
- 탈퇴할 때 음수 캐시백이 남아 있어도 탈퇴되고, 남은 데브머니는 모두 모의계좌로 환불된다.
- 탈퇴하면 PENDING 상태였던 적립 예정 건이 모두 소멸되고 확보 예산이 반환되며, 이후 지급 배치가 그 건을 지급하지 않는다.
- 탈퇴 처리와 거의 동시에 들어온 `debit / credit`은 한쪽만 반영된다. 둘 다 성공하거나, 지갑이 먼저 `WITHDRAWN`으로 바뀌면 나중 `debit / credit`은 거절된다.
- 탈퇴 실행에서 확인받은 금액과 지금 금액이 다르면 거절되고 아무것도 바뀌지 않는다. 지갑이 다른 거래에 잠겨 있으면 그 거래가 끝난 뒤 바뀐 잔액을 보고 거절한다(옛 잔액으로 환불해 충전금이 남는 일이 없다).
- 탈퇴 도중 어느 단계에서 실패해도 환불·원장·적립 소멸·상태 변경이 모두 롤백된다. 같은 회원이 동시에 두 번 탈퇴를 요청해도 환불은 한 번만 일어난다.
- 탈퇴한 회원은 토큰이 유효해도 다음 요청부터 401 `AUTH-004`로 막힌다(열린 경로는 통과).
- 결제 요청에서 PIN이 틀리면 결제도 QR 사용도 일어나지 않고, PIN을 5번 틀리면 잠기며 30분 뒤 풀린다. 10분으로 바꾸는 것은 아래 항목이다.
- 캐시백 잔액이 0 이하이면 결제에서 캐시백 사용액이 거절되거나 0으로 처리된다.
- 지갑 잔액은 원장 합계와 같다(D의 대사).
- `debit`에 지연·예외를 넣으면 호출한 결제 트랜잭션이 전체 롤백된다.

**계정 분리·재가입 ([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절, 구현 전)**

- 점주가 가입하고 로그인 후 PIN을 확인한 뒤 가맹점을 등록할 수 있다. 가입하면 0원인 개인 모의계좌만 생긴다.
- 같은 이메일·전화번호로 이용자와 점주 계정을 하나씩 만들 수 있고, 같은 역할의 중복은 동시 요청에도 거절된다.
- 이용자 계정의 점주 로그인과 점주 계정의 이용자 로그인은 거절된다.
- 이용자는 가맹점을 등록할 수 없고, 점주는 결제·충전·캐시백을 쓸 수 없다. 점주의 QR 생성과 결제 확인은 계속 동작한다.
- 기존 점주 계정으로 점주 로그인과 가맹점 기능을 쓸 수 있고, 운영자 로그인은 그대로 동작한다.
- PIN을 5회 틀리면 10분 잠기고, 잠금 중에는 API를 직접 호출해도 거절되며, 10분이 지나면 별도 처리 없이 다시 쓸 수 있다.
- 탈퇴하면 `users`의 개인정보가 지워지고 암호화 보관 정보와 식별값이 남는다. 암호화 보관에 실패하면 탈퇴 전체가 롤백된다.
- 운영자만 회원 ID로 보관 정보를 조회할 수 있고 조회 기록이 남는다.
- 이메일이나 전화번호가 같은 재가입은 초기 잔액 없이 이전 계좌가 연결된다. 동시에 재가입해도 한 계정에만 연결되고 초기 잔액은 지급되지 않는다.
- 계좌를 연결한 뒤에도 거래가 어느 회원의 것인지 추적할 수 있고, 계좌 잔액 대사가 통과한다.

## 7. 제외·후순위

- 이용자 월 한도·적립 내역 조회 API: B가 제공(이슈 #27)
- 사장님(`OWNER`) 가맹점 정보 입력: 가맹점 도메인에서 담당(가입과 별개)
- `ADMIN`·`OWNER` 전용 가입 화면: 제외. `ADMIN`은 일반 가입 뒤 DB에서 `role`을 직접 변경하고, `OWNER`는 가맹점 등록 시 자동 승격. **`OWNER` 가입 화면은 [3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절에서 추가하기로 바꿨다**
- `OWNER` 권한 신청·승인 기능: 제외. 가맹점을 등록하면 자동으로 승격된다(이슈 #150). **[3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절을 구현하면 자동 승격은 없어지고 점주로 가입한다**
- `ADMIN`의 시민·점주 기능: 제외(운영 전용). 필요하면 일반 계정을 따로 사용
- 한 계정이 여러 역할을 동시에 갖는 구조(역할 테이블): 제외
- 비밀번호 변경·찾기, 프로필 수정: 범위 밖(기획서에 없음)
- 소셜 로그인: 제외(기획서에 없음)
- **MVP 중간 결과물 이후로 미룬 것**: 리프레시 토큰·로그아웃(이슈 #190), 이메일 인증 PIN 잠금 해제(U7), 토스페이먼츠 충전(W6)
- **이후에 할 것**: 점주 탈퇴 허용, 해지 정산의 점주 개인 모의계좌 이체, 보관 정보 조회 화면, 보관 기간이 지난 데이터의 삭제 처리, 재가입 시 월 적립 한도 이어받기(B와 협의), 로그인 시도 횟수 제한

## 8. 개발하면서 판단할 것

번호는 우선순위가 아니라 식별용이다. 방향은 제안이다.

### 1. 로그인 토큰 방식과 리프레시 토큰 저장소

- **결과(부분 해결)**: JWT access 30분은 구현했다. **리프레시 토큰은 MVP 중간 결과물 이후로 미뤘다**(이슈 #190). 시연 중 30분마다 다시 로그인해야 한다.
- **방향(이후)**: 무작위 값의 SHA-256 해시를 `refresh_token` 테이블에 저장(ERD 수정), HttpOnly 쿠키, 회전과 재사용 감지(그 로그인의 토큰 모두 폐기), 재발급 때 DB의 현재 역할·상태를 읽는다(탈퇴한 회원은 재발급 불가). 탈퇴할 때 토큰 일괄 폐기를 연결한다

### 2. PIN 잠금 해제의 인증번호 저장소와 메일 발송 방식

- **고민**: 인증번호와 만료 시각을 어디에 저장할지, 메일을 어떻게 보낼지
- **결과(임시 해결)**: MVP는 스펙의 대체안인 **30분 자동 해제**로 정했고 구현했다(사용자 결정, 코드 주석에도 임시 방식이라고 적음). 이메일 인증 해제(U7)는 MVP 이후이며, 그때 저장은 테이블 또는 Redis, 발송은 SMTP(로컬 가짜 메일 서버로 시연 가능)로 정한다. 11/26에 이메일 인증 도입 전까지의 잠금 시간을 10분으로 바꾸기로 했다([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절)

### 3. 탈퇴한 회원의 재가입

- **고민**: 같은 이메일·전화번호로 다시 가입할 수 있는지(`users`의 `unique`)
- **결과**: MVP에서는 `unique`를 유지해 재가입을 막는다(가입 `AUTH-001`/`AUTH-002`, 로그인 `AUTH-004`). **허용 여부와 방식은 화요일(11/24) 이후** 정한다([3-7](#3-7-탈퇴-정산)절). 11/26에 재가입 허용과 방식을 확정했다([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절, 구현 전)

### 4. 토스페이먼츠 충전 세부 설계

도입과 전체 흐름은 팀 합의이고, 아래 세부는 정해야 한다.

- **고민**
    - 결제창을 띄울 프론트 화면의 담당
    - 승인은 됐는데 계좌 차감이나 지갑 반영이 실패했을 때 토스 취소로 되돌리는 방식
    - `charge.method`에 기록할 결제 수단 값(토스가 돌려주는 값을 그대로 쓸지)
- **방향**: 프론트 담당은 팀에서 확인한다. 승인 후 실패는 토스 취소로 되돌린다. 결제창 없이 모의계좌에서 지갑으로 충전하는 흐름을 먼저 구현하고, 그 앞에 결제창을 붙인다

### 5. WalletService 시그니처와 거래 type 이름

- **결과(해결)**: B 요청의 도메인 중립 시그니처(`credit`, `debit`)를 기준으로 하고, A의 결제는 사용자가 고른 충전금·캐시백 사용분을 한 번에 넘기는 `debitPayment / creditPaymentCancel`(반환 없음)로 정했다. 거래 `type`은 `CHARGE`, `REFUND`, `PAYMENT_DEVMONEY`, `PAYMENT_CASHBACK`, `PAYMENT_CANCEL_DEVMONEY`, `PAYMENT_CANCEL_CASHBACK`, `CASHBACK_EARN`, `CASHBACK_CLAWBACK`이다([3-5](#3-5-walletservice-ab-연동)절).

### 6. 동시 가입 시 unique 위반 처리

- **고민**: DB `unique` 위반이 지금은 500으로 응답된다.
- **방향**: 저장 시 예외를 잡아 중복 코드(409)로 변환한다. 구현하면서 통합 테스트로 확인

### 7. OWNER 권한 부여 방식과 토큰

- **고민**: `OWNER`를 DB에서 부여하면 이미 발급된 JWT는 옛 역할을 그대로 가진다. 시연에서 시민이 점주가 되는 흐름이 필요한지도 정해지지 않았다.
- **결과(해결)**: 가맹점을 등록하면 한 트랜잭션에서 `OWNER`로 자동 승격하고(이슈 #150), 승격 직후 기존 토큰은 옛 역할이므로 `/api/users/me`의 `needsRelogin`이 `true`가 된다. 프론트는 이때 재로그인을 안내한다(리프레시 토큰 도입 후에는 재발급으로 대체 가능). 점주 가입을 분리하면 승격은 없어진다([3-8](#3-8-계정-분리와-탈퇴재가입-구현-전)절)

### 8. 탈퇴 시 CashbackService.cancel 호출 단위

- **고민**: 탈퇴한 지갑에 PENDING 적립 건이 여러 개 있을 수 있다. B의 `CashbackService.cancel`을 적립 건(`refKey`)마다 하나씩 호출할지, 지갑 단위로 한 번에 처리하는 변형을 B가 따로 둘지 정해야 한다. 둘 다 탈퇴 트랜잭션 안에서 호출해야 하므로, 트랜잭션 참여 방식(`REQUIRED`)과 실패 시 처리도 맞춰야 한다.
- **결과(해결)**: 건별 호출로 구현했다. PENDING 목록을 조회해 건마다 `cancel(paymentId)`를 호출하고, 호출은 탈퇴 트랜잭션에 참여한다. PAID 건에는 호출하지 않는다. B의 확인이 남았다.

### 9. 지갑 잔액을 바꾸는 방식 (낡은 엔티티 문제)

- **고민**: 한 트랜잭션에서 지갑을 먼저 읽은 뒤 잠그면, JPA가 이미 읽은 객체를 그대로 돌려주어 잠근 뒤에도 낡은 잔액을 본다. 그 상태로 저장하면 다른 요청이 커밋한 변경(다른 칸 포함)을 덮어써서 충전이나 캐시백 지급이 사라질 수 있다. 재현 테스트로 확인했다(PR #95 리뷰).
- **현재**: 잠근 직후 DB의 최신 값으로 다시 읽는다(`WalletService`, `ChargeService`의 계좌). 한도 검사는 엔티티가 아니라 값 조회로 잔액을 읽고, 호출한 쪽의 트랜잭션을 필수로 한다(`ChargeLimitService`).
- **방향(나중, 시간이 날 때)**: 잔액 변경을 객체 저장이 아니라 DB가 직접 더하는 조건부 UPDATE(`UPDATE wallet SET balance = balance + :amount WHERE id = :id`)로 바꾼다. 메모리의 낡은 객체에 의존하지 않아 이 문제가 구조적으로 사라진다. 저장 방식을 통째로 바꾸므로 MVP 이후로 둔다.

### 10. 로그인 이후 `userId`로 `walletId`를 찾는 방법

- **고민**: 충전 서비스는 `walletId`를 받는데, 로그인 이후 컨트롤러는 `userId`만 안다. `findByUserId`는 `Wallet` 엔티티를 통째로 읽는다. 이 프로젝트는 `open-in-view` 설정이 없어 기본값(켜짐)이라, 컨트롤러에서 읽은 엔티티도 그 요청의 영속성 컨텍스트에 남아 뒤이은 트랜잭션이 재사용할 수 있다.
- **방향**: `walletId`는 엔티티가 아니라 ID만 읽는 조회로 찾는다. 충전은 지갑·계좌를 잠근 직후 최신 값으로 다시 읽어 이 경우에도 입금·차감이 유실되지 않는다. 로그인(U3·U4) 작업에서 정한다.

### 11. 가입 시 BCrypt를 트랜잭션 밖으로

- **고민**: 비밀번호·PIN 암호화는 느린 연산인데 가입 트랜잭션 안에서 해서 그동안 DB 연결을 잡고 있다. 가입이 모의계좌·지갑까지 만들면서 트랜잭션이 더 길어졌다.
- **방향**: 암호화를 트랜잭션 밖으로 옮긴다. A·B 요구와 무관해서 MVP 이후로 두고 필요하면 이슈로 분리한다.

### 12. 결제 트랜잭션의 리질리언스 적용 경계

- **고민**: A가 결제 트랜잭션에 서킷브레이커·타임아웃·재시도·벌크헤드를 적용한다(C와 공동). 적용 경계가 지갑 호출 지점만인지 트랜잭션 전체인지 정해야 한다(A 기획서 합의 #4). 지갑 호출만 재시도하면 같은 `paymentId`의 재호출은 한 번만 반영되지만, 지갑 예외를 호출한 트랜잭션 안에서 잡고 계속하면 트랜잭션이 롤백 전용이 된다([3-5](#3-5-walletservice-ab-연동)절).
- **방향**: A 기획서가 마감 범위 밖(11/25 이후)으로 분리했으므로 MVP 이후에 A와 정한다.

### 13. 탈퇴한 회원의 결제 취소

- **고민**: 탈퇴한 지갑으로는 환급이 거절되어(WAL-002) 점주가 탈퇴한 회원의 결제를 취소할 수 없다. 지급이 끝난 캐시백의 회수도 같은 이유로 막힌다(이슈 #137 항목 4). 정책이 없다.
- **방향**: 팀에서 정한다. 후보는 ① 탈퇴 전에 취소 가능한 결제가 있으면 막기, ② 탈퇴한 지갑의 취소 환급을 모의계좌로 보내기, ③ 점주 취소는 허용하고 환급만 건너뛰기다. 코드 동결 전에는 ③이 가장 간단하고, ②는 화요일(11/24) 이후에 한다([3-7](#3-7-탈퇴-정산)절).

### 14. 탈퇴 정보의 보관 기간

- **고민**: 암호화해 보관하는 이름·연락처, 식별값, 계좌·거래 기록을 얼마나 보관할지. 가입 동의 문구에 기간이 필요하다. 식별값을 지우면 그 뒤의 재가입은 처음 가입으로 본다.
- **방향**: 가맹점 데이터와 같은 5년을 제안한다. 구현 전에 정한다.
