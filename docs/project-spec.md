# DevPay 기획서

선불 지갑(데브머니)으로 QR 결제하고, 결제액의 일부를 캐시백으로 적립해 주는 모의 간편결제 서비스. 4명이 4주 동안 개발한다. 돈이 움직이는 모든 흐름의 정합성(동시성, 멱등, 원장 대사)이 핵심 과제다.

## 1. 개요

| 항목 | 내용 |
|---|---|
| 역할 | USER(이용자), OWNER(사장님), ADMIN(운영자) |
| 기술 | Spring Boot 4.1.2, Java 25, Gradle |
| 핵심 과제 | 결제 동시성, 멱등키, 원장(INSERT only)과 잔액의 일치, 캐시백 예산·한도 관리 |

### 결제 흐름
1. 가입 시 지갑과 모의계좌 생성 (초기 잔액 100만원)
2. 모의계좌에서 데브머니로 충전 (환불은 반대 방향)
3. 사장님이 가맹점을 등록하고 고정 QR 또는 금액이 담긴 동적 QR(3분 만료) 발급
4. 이용자가 QR을 스캔하고 간편 비밀번호(PIN 6자리)로 결제. 데브머니와 캐시백을 함께 쓸 수 있음
5. 결제 다음날 00:00 기준 3일 뒤 캐시백 적립 지급 (배치)
6. 사장님이 필요하면 전액 취소, 매일 00:10 일 정산, 00:30 원장 대사

## 2. 기능 목록

## 4. 캐시백·예산 정책

- **적립**: 적립 대상 가맹점에서만, 데브머니 사용분 × 접수 시각 요율. 적립·보유·회수는 소수점을 유지하고, 결제에 사용하는 금액만 1원 단위로 제한한다.
- **월 한도**: 결제한 달(한국 시간) 기준, 적립 예정 포함. 취소 시 원래 결제월에 한 번만 복구하고, 지난달 결제를 취소해도 이번 달 한도는 늘지 않으며, 복구되어도 과거에 적립받지 못한 거래에 소급 적립하지 않는다.
- **예산 구조**: 연 예산 아래 월 예산을 둔다. 월 예산 기본 배정의 합은 연 총예산을 넘을 수 없다. 결제 시 연 예산과 월 예산을 함께 차감한다.
- **이월**: 월말 잔여를 계산해 다음 달 예산으로 이월한다. 이월 시점은 지급 예정 3일 구간이 지난 뒤로 하고, 마감 후 취소는 현재 월 예산에 가산하는 규칙을 둔다.
- **대비금**: 최근 완료된 7일의 일평균 지급액 × 5일.
- **취소**: 지급 전 취소는 확보 예산 반환, 지급 후 회수의 예산 복구는 별도 정책. 음수 발생만으로 복구하지 않는다.

## 5. 공통 규칙

| 구분 | 내용 |
|---|---|
| 접근 권한 | 이용자는 본인 계좌·거래, 사장님은 본인 매장 거래만 접근 |
| 중복 요청 | 같은 요청은 한 번만 처리. 같은 요청 키로 금액·대상을 바꾸면 거절 |
| 최종 검증 | PIN 사전 검증만으로 처리하지 않고, 실제 금액 처리 요청에서도 인증 유효성·잔액·QR 등을 확인 |
| 동시 처리 | 결제·환불·지급·취소·탈퇴가 겹쳐도 금액과 기록이 일치 |
| 실패 처리 | 실패 상태·사유는 기록하되 금액 변경은 남기지 않음 |
| 완료 기준 | 정상·실패·중복·동시 요청에서 기대 결과를 기능별로 정의 |

## 6. 확정 필요 사항

개발 시작 전(1주차 초)에 결정한다. 기본값은 제안이다.

| # | 항목 | 관련 기능 | 제안 기본값 |
|---|---|---|---|
| 1 | 로그인 토큰 방식 | 로그인 | JWT Access / Refresh |

| 3 | 보유 한도, 월 충전 한도 | 충전 | 보유 100만원, 월 충전 100만원 |
| 4 | 부분 환불 허용 여부 | 환불 | 허용 (원문 기준) |
| 5 | 적립 대상 가맹점 기준 | 가맹점 등록 | 가맹점별 플래그 |
| 6 | QR 만료 기준 시각 | 동적 QR 생성 | 생성 시각 + 3분 |
| 7 | 대비금 기준 | 예산 관리 | 최근 7일 일평균 × 5일 (원문 기준) |

## 7. 원장 대사 7종

| # | 대사 |
|---|---|
| 1 | 모의 계좌 잔액 = 초기 지급을 포함한 계좌 원장 합계 |
| 2 | 데브머니 잔액 = 데브머니 원장 합계 |
| 3 | 캐시백 잔액 = 실제 지급·사용·복원·회수·정산·소멸 원장 합계 |
| 4 | 각 충전의 계좌 차감액 = 지갑 증가액 |
| 5 | 각 환불의 지갑 차감액 = 계좌 증가액 |
| 6 | 당일 순매출 = 당일 결제 총액 - 취소 총액 |
| 7 | 정산 확정액 + 다음 날 이월액 = 당일 순매출 + 전일 이월액 |

### 실행 방식
- 매일 00:30, 일 정산(00:10)이 끝난 뒤 실행. 6, 7은 정산 후에만 검사 가능
- 7개를 각각 독립 실행한다. 하나가 실패해도 나머지는 계속 돈다
- 범위는 어제 바뀐 것만 (1~3은 어제 거래가 있던 계좌·지갑, 4~5는 어제 완료된 충전·환불, 6~7은 어제 날짜 정산 행)
- 결과는 `reconciliation_result`에 대사 번호, 대상 날짜, 검사 건수, 불일치 건수, 불일치 대상 ID를 INSERT
- 자동으로 고치지 않는다. 불일치는 운영자가 원장을 보고 원인을 찾는다
- 전체 검사는 주 1회 또는 운영자가 수동 실행할 때만

## 8. ERD 변경 사항

| 구분 | 테이블 | 비고 |
|---|---|---|
| 변경 | `cashback_budget` → `cashback_annual_budget` | 연 예산 |
| 신규 | `cashback_monthly_budget` | 월 예산, 이월 유입, 집행액, 마감 시각, 낙관적 락 |

## 9. 잘못 해석되기 쉬운 규칙 (주의)

| 위치 | 주의할 점 |
|---|---|
| 결제 취소 | 예산 반환은 지급 전 취소에만 해당. 지급 후 회수는 별도 정책 |
| 월 한도 | "결제한 달"은 최초 서버 접수 시각이 속한 한국 시간 기준 월 |
| 결제 재조회 | 조회 시간 초과만으로 실패 처리하지 않음. 서버에서 확정된 실패만 실패로 표시 |
| 결제 취소 | 조건부 UPDATE만으로 안전하지 않음. 상태 변경, 사용액 복원, 혜택 회수, 한도 복구, 매출 차감을 함께 처리 |
| 부분 환불 | 충전금 일부 환불은 허용 가능. 부분 **결제 취소**와 구분 |
